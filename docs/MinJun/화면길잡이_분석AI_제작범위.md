## 1. A — 분석 모듈 (Kotlin)

### 1-1. 구조

```
MainActivity ──▶ ChannelCodec ──▶ Analyzer ──▶ logic/GuideLogic
 (채널 등록)     (JSON ↔ 자료형)   (ML Kit 호출, 순서)   (규칙: 순수 함수)
```

| 파일 | 책임 | Android 의존 | 시험 |
|---|---|---|---|
| `MainActivity.kt` | 채널 `screen_guide/analyze` 등록, 메서드 `analyze`를 코덱에 넘김 | 있음 | 실기기 |
| `ChannelCodec.kt` **(새로 만듦)** | 요청 Map → `AnalyzeRequest`, 결과 → 응답 Map. 형식이 틀리면 오류 응답 | 없음 | JUnit: 예시 파일 대조 |
| `Analyzer.kt` | 디코딩 → OCR → 요소 정리 → 규칙 호출 → 시간 측정 | 있음 | 실기기 |
| `logic/GuideLogic.kt` | 화면 식별, 대상 찾기, 개인정보 정규식·병합·가림 | 없음 | JUnit (지금 28건) |

`ChannelCodec`을 따로 떼는 이유는 하나다. 채널 형식이 계약과 같은지를 **기기 없이 JUnit으로** 확인하려면 변환 코드가 Android에 묶여 있으면 안 된다.

### 1-2. 처리 순서

```
imagePath ─▶ 디코딩 ─▶ OCR ─▶ 요소 정리 ─┬▶ 화면 식별 ─▶ 대상 찾기
                                         └▶ 개인정보: 개체 추출 + 정규식 ─▶ 병합 ─▶ 가림
                                                              ─▶ 응답
```

### 1-3. 입력과 출력 (계약 v1 그대로)

요청에서 내가 읽는 것.

| 필드 | 쓰임 |
|---|---|
| `requestId` | 응답에 그대로 돌려준다 |
| `imagePath` | 앱 임시 폴더의 파일 경로 |
| `guidance.screens[]` | 화면별 `screenId`와 `anchors`. 화면 식별에 쓴다 |
| `target.selector` | 있을 때만 대상 찾기를 한다 |

응답으로 내가 채우는 것.

| 필드 | 규칙 |
|---|---|
| `status`, `errorCode` | 실패도 예외가 아니라 응답 본문. 코드는 `NO_PATH`, `IMAGE_READ_FAILED`, `ANALYSIS_FAILED` |
| `imageSize` | 화면에 보이는 방향 기준 (세로 사진은 회전 뒤 값) |
| `screenId` | 식별 못 하면 `null` |
| `elements[]` | `label`, `box`(원본 픽셀 `[left, top, right, bottom]`) |
| `target` | 요청에 없었거나 후보가 0개 또는 2개 이상이면 `null` |
| `pii[]` | `type`(9개 중 하나), `masked`(앞 3자·뒤 2자), `elementIndex` |
| `piiEngine.mlkit` | `failed`여도 정규식 결과로 진행 |
| `timingMs` | 디코딩 시작부터 응답 직전까지 |

### 1-4. 고칠 규칙 다섯 가지

| # | 지금 코드 | 문제 | 고친 규칙 | 시험 |
|---|---|---|---|---|
| R1 | 앵커가 줄 전체 또는 줄 안의 단어와 같으면 1개로 셈 | "알림 설정" 한 줄이 앵커 `알림 설정`과 `설정`을 둘 다 채운다 | 앵커 2개 이상이 **서로 다른 요소**에서 맞아야 한다 | 한 줄만 있는 화면 → 미식별 |
| R2 | 조건을 채운 첫 화면을 고름 | 결과가 맵에 적힌 순서로 정해진다 | 맞은 수가 **가장 많은 화면**. 같은 수면 미식별 | 2:2 → `null`, 3:2 → 3인 화면 |
| R3 | 정확히 같은 요소 중 첫 번째를 고름 | 같은 글자가 둘이면 엉뚱한 곳을 가리킬 수 있다 | 정확 일치가 **하나일 때만**. 없으면 길이가 같고 한 글자만 다른 요소가 하나일 때만 | 같은 글자 2개 → `null` |
| R4 | 정규식이 `\b` 경계를 씀 | 한글과 숫자가 붙은 곳에서 경계가 어긋난다 | 앞뒤가 숫자가 아닌 조건으로 교체 | 유형별 시험 세트 |
| R5 | 유형 이름에 엔진 이름이 섞임 | 화면이 유형을 고정된 값으로 다룰 수 없다 | 9개로 고정: `주민·외국인등록번호`, `휴대전화`, `유선전화`, `계좌번호 추정`, `전화`, `이메일`, `주소`, `카드`, `URL` | 9개 밖의 값이 나오지 않음 |

R1~R3는 "모르면 추정하지 않는다"는 한 가지 원칙에서 나온다. 틀린 곳을 가리키는 것이 못 찾았다고 말하는 것보다 나쁘다.

### 1-5. 내보내지 않는 것

| 무엇 | 어디에서 막나 | 확인 |
|---|---|---|
| 원본 이미지 | 응답에 이미지 칸이 없다 | 응답 키 대조 |
| 개인정보 후보 원문 | `pii[].masked`만 있다 | JUnit: 응답에 원문 문자열 없음 |
| Logcat의 인식 글자·가린 값 | 로그는 줄 수와 시간만 | 분석 중 Logcat에 인식 글자 0줄 |
| 네트워크 | 이미지·글자를 보내는 코드가 없다. OCR 모델은 앱에 들어 있다 | 12/2 외부 전송 확인 |

개체 추출 모델은 첫 실행 때 내려받는다. 없으면 기다리지 않고 정규식만 쓰고 `piiEngine.mlkit`에 `failed`를 적는다. "네트워크를 전혀 쓰지 않는다"가 아니라 "**사용자 이미지와 글자는 나가지 않는다**"가 정확한 표현이다. 발표자료와 PRIVACY.md에도 이 표현을 쓴다.

## 2. B — 기능 맵 내용

저장 형식과 읽는 코드는 정혁이 맡고, **안에 들어갈 내용**은 내가 쓴다. 앵커와 선택자가 실제 OCR에서 어떻게 읽히는지는 분석기를 돌려 봐야 알기 때문이다. (규격 8장 4번, 11/13 확인 대상)

### 2-1. 만드는 순서

1. 대상 앱의 화면을 캡처한다 (화면마다 2장 이상, 내용이 다른 상태로).
2. 분석기로 돌려 인식된 줄을 본다.
3. 화면마다 앵커를 고른다. 그 화면에 항상 있고 다른 화면에는 없는 줄.
4. 단계마다 선택자를 고른다. 한 줄로 읽히는 글자.
5. 단계 문구(`instruction`, `result`)를 쓴다.
6. 캡처한 이미지로 식별과 대상 찾기를 확인한다.

### 2-2. 지켜야 하는 규칙 (맵 공용 시험이 확인)

| 규칙 | 내가 확인할 때 보는 것 |
|---|---|
| 화면 ID는 `앱.화면` | 전체에서 겹치지 않는가 |
| 화면마다 앵커 2개 이상, 서로 포함하지 않음 | `설정`과 `알림 설정` 같은 쌍이 없는가 |
| 기능마다 단계 1~5개 | |
| 단계의 `screenId`가 맵에 있고, 첫 단계의 화면이 기능의 시작 화면 | |
| 선택자는 2자 이상, 한 줄로 읽히는 글자 | 실제 OCR 결과에 그 줄이 **하나만** 있는가 (R3) |

### 2-3. 완료 기준

| # | 제공물 | 완료 기준 | 마감 |
|---|---|---|---|
| B1 | 기능 3개의 맵 내용 (하나는 화면 두 개 이상에 걸침) | 실제 스크린샷으로 식별·대상 찾기 확인, 맵 공용 시험 통과 | 11/25 |

## 4. C — 형주에게서 옮겨 받는 일 (11/13 확정 대상)

화면을 그리지 않는 계산과 시험이다. 폴더 소유는 형주에게 두고, 파일만 내가 만들어 PR로 넣는다. 합계 약 11시간.

### 4-1. 단계 맞추기 함수 (2시간)

사용자가 안내 도중 다른 화면을 올렸을 때 어느 단계로 갈지 정한다.

```dart
// [제안] 돌려주는 값: 옮겨 갈 단계 번호. 맞는 단계가 없으면 null
int? alignStep(List<GuideStep> steps, int current, String screenId)
```

| 순서 | 규칙 |
|---|---|
| ① | `current` 이후(포함)에서 `screenId`가 같은 **첫** 단계 |
| ② | 없으면 `current` 이전에서 `screenId`가 같은 **마지막** 단계 |
| ③ | 그래도 없으면 `null` → 화면은 "이 기능의 화면이 아니에요" |

앞으로 가는 쪽을 먼저 보는 이유: 사용자는 보통 다음 화면으로 넘어간 것이다. 뒤로 간 경우는 그다음에 본다.

시험 3경우: 다음 단계의 화면을 올림(①), 이전 화면으로 돌아감(②), 관계없는 화면(③). 덧붙여 같은 화면의 단계가 연달아 있을 때 지금 단계에 머무는지 확인한다.

### 4-2. 공유 텍스트 만들기 함수 (2시간)

```dart
// [제안]
String buildShareText(String actionTitle, List<String> stepInstructions)
```

- 재료는 **기능 제목과 단계 문구뿐**이다. 둘 다 기능 맵에 사람이 써 둔 글이다.
- 함수의 인자에 분석 결과가 없다. 그래서 화면에서 읽은 글자가 섞일 길이 없다. 이것이 이 함수를 따로 두는 이유다.
- 시험: 인식 요소의 글자와 가린 값을 가진 세션에서 만든 텍스트에 그 문자열이 들어 있지 않다.

### 4-3. 좌표 변환 함수 (1시간)

```dart
// [제안] box: 원본 이미지 픽셀 [left, top, right, bottom]
Rect mapBox(List<int> box, Size imageSize, Size shownSize)
```

- 이미지를 가로세로 비율을 지켜 `shownSize`에 맞춰 보여 줄 때, 원본 픽셀 상자를 화면 좌표로 바꾼다.
- 지금 `ScreenImage` 안의 계산은 맞게 동작한다. 고치는 것이 아니라 **밖으로 빼서 시험을 붙이는** 일이다.
- 인터페이스로 만들지 않는다. 구현이 하나뿐인 계산이다.
- 시험: 같은 비율, 가로가 남는 경우, 세로가 남는 경우, 이미지 모서리의 상자.

### 4-4. 복구 표 초안 (2시간)

오류 코드 → 문구와 복구 버튼. 화면은 이 표만 읽는다. **문구와 버튼 배치의 최종 결정은 형주**이고, 나는 코드별로 무엇이 일어난 것인지 아는 쪽이라 초안을 낸다.

| 오류 코드 | 누가 내나 | 뜻 | 문구 (초안) | 버튼 (초안) |
|---|---|---|---|---|
| `PERMISSION_DENIED` | 흐름 (입력 결과) | 권한 거부 | 권한 안내 화면 | `settingsOpenPermission`, `captureGallery` |
| `IMAGE_READ_FAILED` | 흐름 또는 Kotlin | 파일을 못 읽음 | "이미지를 읽지 못했어요" | `captureCamera`, `captureGallery`, `navHome` |
| `NO_PATH` | Kotlin | 요청에 경로가 없음 (코드 결함) | "문제가 생겼어요. 다시 시도해 주세요" | `captureRetake`, `navHome` |
| `ANALYSIS_FAILED` | Kotlin | OCR 실행 실패 | "분석하지 못했어요" | `captureRetake`, `navHome` |
| `UNKNOWN_SCREEN` | 흐름 (`screenId` 없음) | 지원 화면이 아니거나 글자가 부족 | "다시 촬영해 주세요" | `captureRetake`, `captureCamera`, `captureGallery`, `navHome` |
| `NO_TARGET` | 흐름 (`target` 없음) | 화면은 맞는데 대상이 안 보임 | "이 화면에서 찾지 못했어요" | `captureRetake`, `navHome` |
| `TIMEOUT` | 흐름 | 3초를 넘김 | 화면 없음 (표시만) | — |
| `CANCELLED` | 흐름 | 사용자가 취소 | 화면 없음 (이전 장면) | — |

추정 안내는 하지 않는다. "아마 여기일 거예요" 같은 문구는 표에 넣지 않는다.

### 4-5. Flutter 쪽 분석기 파일 (2시간)

| 파일 | 내용 |
|---|---|
| 채널 분석기 | `ScreenAnalyzer` 구현. 채널을 부르고 응답 JSON을 자료형으로 바꾼다. 채널 예외와 형식 불일치도 `status: error`와 같은 모양으로 바꾼다 |
| 가짜 분석기 | Kotlin 규칙(R1~R3)의 복사본. 기기 없이 흐름을 시험할 때 쓴다 |
| 예시 파일 | `contract_fixtures/analyze/`. Kotlin JUnit과 Dart 시험이 같은 파일을 읽는다 |

규칙을 고치면 이 셋을 같이 고쳐야 한다. 그래서 규칙을 고치는 사람이 맡는다.

### 4-6. "확인 화면 없이 공유되는 길 0개" 시험 (2시간)

- `Sharer.shareText`가 불리는 모든 길이 공유 전 확인 화면을 지나는지 본다.
- 방법: 가짜 `Sharer`를 끼우고, 확인 화면을 거치지 않은 상태에서 공유 버튼 ID를 보냈을 때 호출 횟수가 0인지 확인한다.
- 형주의 흐름 코드가 있어야 쓸 수 있어 11/27 주에 한다.

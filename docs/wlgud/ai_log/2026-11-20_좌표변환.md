## 3. 하나씩 물어본 것

| 단위 | 물어본 것 | AI의 설명 | 내 판단 |
|---|---|---|---|
| D-1 | 왜 클래스나 포트가 아니라 맨 바깥 함수 하나인가 | 구현이 하나뿐인 순수 계산이라 갈아 끼울 일이 없다(X7). 클래스로 감싸면 쓰지 않는 껍데기만 생긴다. 같은 값을 넣으면 늘 같은 값이 나오니 시험도 값만 비교하면 된다 | |
| D-1 | 왜 `sx`·`sy`를 따로 계산하나 | 화면에 그린 크기의 비율이 원본과 조금이라도 다르면(반올림, `BoxFit.fill`) 하나의 비율로는 한쪽이 어긋난다. 따로 곱하면 어떤 크기에 그려도 같은 자리가 된다 | |
| D-1 | `Rect.zero` 한 줄은 왜 넣나 | 원본 크기가 0이면 0으로 나눠 무한대가 되고, 그 자리에 그리려다 화면이 깨진다. 정상 응답에선 없지만 계약상 `imageSize`가 없으면 0이 된다(`analysis.dart` 296줄) | |
| D-1 | 테두리 여유(`inflate`)는 왜 함수에 안 넣나 | 몇 픽셀 띄울지는 그리는 방식(디자인)이라 화면 부품이 정한다. 좌표 계산과 섞으면 시험이 디자인 값에 묶인다 | |
| D-1 | 문서의 "↔"인데 왜 한 방향만 만드나 | 화면 → 원본으로 거꾸로 바꾸는 곳이 없다(실시간 오버레이는 제외 범위). 쓰지 않는 함수는 만들지 않고, 필요해지면 그때 추가한다 | |
| D-2 | 왜 화면을 띄우지 않고 숫자만 비교하나 | 순수 함수라 넣은 값과 나온 값만 보면 된다. 그리는 것은 D-3 위젯 시험에서 본다 | |
| D-2 | 왜 "거의 같음(`closeTo`)"이 아니라 정확히 같은지(==) 보나 | 비율을 ½·¼처럼 컴퓨터가 정확히 표현하는 값으로 골랐다. 그래서 오차가 없고 시험이 읽기 쉽다 | |
| D-2 | 가로·세로가 다른 비율 시험(3번)은 왜 꼭 있어야 하나 | 나머지 시험은 가로·세로 비율이 같아서, 세로에 `sx`를 잘못 곱해도 통과한다. 일부러 그렇게 바꿔 보니 7개 중 3번 하나만 실패했다 | |
| D-2 | 계약 예시 파일 값은 왜 파일을 읽지 않고 숫자로 적나 | 파일 읽기는 `fixtures_test.dart`가 이미 본다. 이 시험은 계산만 본다. 어디서 온 숫자인지 시험 이름에 적었다 | |
| D-3 | 크기 0은 왜 계약(`analysis.dart`)이 아니라 화면 부품에서 거르나 | 계약의 `AnalysisResult`는 크기가 없으면 기본값이 0이다(245·260줄). 즉 0 = "크기 없음"이 계약의 약속이라 화면이 그렇게 읽으면 된다. 계약을 null로 바꾸면 공동 파일과 남의 시험까지 건드린다. 흐름에서 "실패"로 만드는 것은 문서(3.3)에 없는 규칙이고 글 안내까지 막는다 | |
| D-3 | 설명은 `hasSize`(참/거짓)였는데 왜 `source`(`Size?`)가 됐나 | Dart는 참/거짓 변수만으로는 `w`·`h`가 null이 아님을 알지 못해서 `w!`처럼 강제로 써야 한다. 크기를 믿을 수 있을 때만 `Size`를 만들고 아니면 null로 두면, 조건은 한 번만 쓰고 아래에서는 `source`를 바로 쓸 수 있다 | |
| D-3 | 왜 도우미 `map`을 남겼나 | 쓰는 곳이 세 군데(어둡게 칠할 구멍, 얇은 테두리, 굵은 테두리)라 같은 인자를 세 번 쓰지 않는다. 세 줄은 그대로라 바뀐 곳이 한눈에 보인다 | |
| D-3 | 시험 1번 정답이 왜 (25,50,75,100)이 아니라 (21,46,79,104)인가 | `mapBox` 결과에 화면 부품이 테두리 여유 4를 더한다(`inflate(4)`). 여유는 함수가 아니라 그리는 쪽 일이라 D-1에서 함수에 넣지 않았다 | |

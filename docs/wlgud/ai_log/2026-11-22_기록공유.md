## 3. 하나씩 물어본 것

| 단위 | 물어본 것 | AI의 설명 | 내 판단 |
|---|---|---|---|
| 5-1 | 5번 자체가 버튼 일인가 | 아니다. 5번은 안내가 끝난 뒤 쓰는 화면 셋(기록·설정·공유)이다. 등록부는 그 버튼들이 "누르면 무엇을 하나"를 빠짐없이 적는 바탕이라 먼저 한다 | |
| 5-1 | 관문과 등록부는 무엇이 다른가 | 관문(`allows`, 단계 설정표) = 지금 눌러도 되나. 등록부(`dispatch`의 switch) = 누르면 무엇을 하나 | |
| 5-1 | 왜 `default:`를 지우나 | `default`가 있으면 ID를 추가하고 처리를 잊어도 조용히 "준비 중"이 된다. 지우면 Dart가 빠진 갈래를 컴파일 오류로 알려 준다. 갈래 하나를 일부러 지워 `non_exhaustive_switch_statement` 오류가 나는 것을 확인했다 | |
| 5-1 | 왜 `ActionRegistry` 클래스를 안 만드나 | 11/14 결정 ①(switch 유지), 역할설계 U4가 구현을 "`switch` 문"으로 적음, 일정_현실검토 3-2가 같은 방식을 제안. 컴파일러가 "모든 ID에 핸들러"를 대신 확인한다. 시스템설계 6-2의 `ActionRegistry`와는 다르다 | |
| 5-1 | 시험은 무엇을 확인하나 | ① '준비 중' 목록이 정한 13개와 같다 (기능을 만들면 시험도 같이 고쳐야 해서 남은 일이 보인다) ② 28개 모두를 `handle`로 눌러, 목록에 있는 것만 "준비 중" 문구가 나온다 ③ 화면에서(관문을 거쳐) 준비 중 버튼을 누르면 화면은 그대로, 문구만 | |
| 5-1 | 왜 `handle`을 따로 열었나 (점검) | 관문이 막는 버튼은 `dispatch`로 누를 수 없어 홈에서 13개 중 3개만 확인됐다. `sharePrepare`에 진짜 처리를 넣고 목록에서 안 빼도 시험이 통과하는 것을 실험으로 확인 → 관문 없이 처리만 하는 `handle`을 시험 전용(`@visibleForTesting`)으로 열었다. 화면은 계속 `dispatch`만 부른다 | |

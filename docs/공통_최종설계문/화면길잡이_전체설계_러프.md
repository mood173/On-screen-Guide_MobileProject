# 화면길잡이 전체 설계 (러프)

> 기준: 「개발 기본 규칙 — 백로직과 프론트로직을 함께 설계하기」(4축 + 5계층 + 연결표).
> 대상: Flutter(UI·흐름) + Android Kotlin 모듈(분석) + Firebase(기능 맵 배포만).
> 상태: 러프 설계. 클래스 이름은 가칭이며, 구현하면서 바꿔도 된다. 바꾸면 이 문서의 계약표만 같이 고친다.

---

## 0. 목적 고정 (사용자 동작 하나)

**"안내받고 싶은 앱 화면을 찍거나 고르면, 그 화면에서 원하는 기능까지 단계별로 짚어 주고, 공유하기 전에는 개인정보를 가려 준다."**

이 문장에서 나오는 동작 5개가 설계 전체의 기준이다.

| # | 사용자 동작 | 기대 결과 | 요구사항 |
|---|---|---|---|
| A1 | 화면을 찍거나 갤러리에서 고른다 | 이미지가 분석 대기 상태가 된다 | F01 |
| A2 | 분석을 시작한다 | 어떤 앱의 어떤 화면인지 식별된다 | F02, F03 |
| A3 | 원하는 기능을 고르고 안내를 따라간다 | 단계마다 누를 곳이 강조된다 | F04, N01 |
| A4 | 결과를 공유한다 | 개인정보 후보를 확인·가린 뒤 공유된다 | F03, F06, NFR-01 |
| A5 | 지난 안내를 다시 본다 | 기록에서 다시 열린다 | F05 |

시스템이 스스로 시작하는 동작 1개: **S1 앱 시작 시 기능 맵 확인·교체 (B01·B02)**.

## 1. 백로직 — 내부 구조에서 기능으로

### 1.1 규모: 시스템 (아키텍처 스타일, MACRO)

| 결정 | 내용 | 이유 |
|---|---|---|
| **모놀리식 온디바이스 앱** | 분석·안내·기록이 전부 기기 안 한 앱에서 돈다 | NFR-01(원본·OCR 원문이 기기 밖으로 안 나감), NFR-02(오프라인) |
| **클라이언트–서버는 기능 맵 배포에만** | 앱은 Firebase에서 기능 맵을 **받기만** 한다. 사용자 데이터는 올리지 않는다 | B01·B02. 서버 의존을 한 경계에 가둔다 |
| **파이프–필터 (분석 내부)** | 이미지 → 전처리 → OCR → UiElement 변환 → 화면 식별 → 대상 찾기 → 개인정보 검출 → 병합·마스킹 | 단계마다 데이터 형태가 바뀌고, 단계별 단위 시험이 쉽다 |
| **계층형 (각 모듈 안)** | 수직 4층(1.3) 위→아래 호출만 | 순수 규칙을 엔진·UI에서 떼어 냄 |

### 1.2 규모: 영역·모듈 (아키텍처 패턴, MESO)

| 영역 | 패턴 | 적용 |
|---|---|---|
| Kotlin 분석 코어 | **헥사고날** | 코어(GuideLogic 계열)는 import 0. 포트 `OcrEngine`, `EntityExtractor`는 코어 패키지가 소유. ML Kit·MethodChannel은 어댑터 |
| Flutter 화면 | **MVC(MVVM 변형)** | M = 도메인 상태(GuideSession 등), C = Controller(흐름·UseHandle 호출), V = 위젯. V는 C를 인터페이스(화면 계약)로만 안다 |
| 기능 맵·기록 | **Repository** | 저장 기술(Firestore, 로컬 파일/DB)을 UseCase에서 감춘다 |
| 채널 경계 | **외부 형식 격리(코덱)** | MethodChannel의 `Map<String, Object>`는 양쪽 코덱에서만 다룬다. 안쪽은 DTO만 안다 |

### 1.3 수직 (책임과 의존 방향)

의존: **엔티티 ← 유스케이스 ← 데이터 계층 ← 세부사항** / 제어: 엔티티 → … → 세부사항.

| 층 | Kotlin 분석 모듈 | Flutter 앱 | 규칙 |
|---|---|---|---|
| **엔티티** | `UiElement`, `Box`, `ScreenId`, `GuidanceMap`, `PiiType`(enum), `PiiCandidate` / 순수 함수 `norm`, `hasAnchor`, `identifyScreen`, `findTarget`, `regexCandidates`, `merge`, `mask` | `GuideStep`, `GuideSession`, `FlowState`(enum), `AnalysisResult`(DTO), `FeatureMap` | Android·Flutter import 0. JUnit / flutter_test로 단독 실행 |
| **유스케이스** | 키맨 `AnalysisCoordinator` (파이프라인을 순서대로 호출, 결과 집계) | 키맨 `GuideSessionController` / 관리자 `GuideSequence`(1.5) | 흐름과 경우의 수. 외부는 포트로만 |
| **데이터 계층** | 파서 `MlKitTextParser`(ML Kit Text → `UiElement`), 코덱 `ResultCodec`(DTO ↔ Map) | 코덱 `AnalysisCodec`, 파서 `FeatureMapParser`(Firestore 문서 → `FeatureMap`, 해시·서명·스키마 검증), `HistoryRepository` | 세부사항의 형식을 엔티티 형식으로 번역 |
| **세부사항** | ML Kit, `MainActivity`(채널 등록), 오버레이 `WindowManager` | Flutter 위젯, image_picker, share_plus, Firebase SDK, 파일 저장 | 교체 가능. 시험에서는 가짜로 바꾼다 |

**경계 계약 소유:** 채널 너머로 가는 `AnalysisResult`는 **Flutter 쪽 유스케이스가 소유하는 계약**이다. Kotlin은 그 계약에 맞춰 내보낸다. 내보내는 것은 화면 ID, 목표 요소 위치, 표시용 짧은 라벨, 개인정보 후보 위치뿐이다. **OCR 원문 전체는 넘기지 않는다** (테스트 보고서 3.3에서 지적한 차이).

### 1.4 수평 (기능·도메인 모듈)

각 모듈이 자기 수직 스택(엔티티→유스케이스→데이터→세부사항)을 갖는다. 모듈끼리는 직접 호출하지 않고 **계약(DTO·인터페이스)** 으로만 주고받는다.

| 모듈 | 요구사항 | 소유 상태 | 주고받는 것 | 쪽 |
|---|---|---|---|---|
| **Capture 입력** | F01, DENY | 선택된 이미지 경로, 권한 상태 | → Analysis: 이미지 경로 | Flutter |
| **Analysis 분석** | F02, F03 | 없음(무상태 파이프라인) | ← 경로 + 기능 맵 / → `AnalysisResult` | Kotlin |
| **Privacy 개인정보** | F03, F06, NFR-01 | 후보 목록, 사용자 확인 여부 | ← 후보 위치 / → 가린 이미지 | Kotlin(검출) + Flutter(확인 UI) |
| **Guide 안내** | F04 | `GuideSession`(현재 단계) | ← 화면 ID·대상 / → 단계별 강조 정보 | Flutter |
| **Overlay 오버레이** | N01 | 오버레이 표시 여부 | ← `GuideStep`(같은 계약) | Kotlin 렌더러 |
| **History 기록** | F05 | 기록 목록 | ← 완료된 세션 요약 | Flutter |
| **Share 공유** | F06 | 없음 | ← 가린 이미지 | Flutter |
| **FeatureMap 기능 맵** | B01, B02 | 현재 맵 버전 | → Analysis·Guide에 맵 제공 | Flutter(배포) + Kotlin(사용) |
| **Settings 설정** | NFR-03 | 글자 크기, 강조 색 | → 렌더러 전체 | Flutter |

관리자 분류(내 수평 기준)에 대응:

| 관리자 | 화면길잡이에서 | 비고 |
|---|---|---|
| 시퀀스 관리자 | `GuideSequence` (단계 시퀀스) | 1.5 |
| 리소스 관리자 | `FeatureMapRepository` (맵 버전 추적·원자 교체·롤백) | B02 |
| 시스템 데이터 관리자 | `SettingsStore`, `HistoryRepository` | 사용자 데이터 / 앱 흐름 데이터 구분 |
| 팩토리 관리자 | `bootstrap()` = 조립기 (실제/가짜 구현 생성) | 테스트와 공유 |
| 엔진축 (등록·무결성) | `ActionRegistry` + 등록 검사 시험, `Tid` 이름표 규칙 | 2.3 |
| UI 관리자 | `AppShell` | 2.1 |

### 1.5 프로세스 (진입 주체·순서·생애주기·상태 전이)

**진입 주체**

| 주체 | 진입 | 예 |
|---|---|---|
| 사용자 | 버튼 → 기능 ID | 촬영, 분석, 다음 단계, 공유 |
| 시스템 | 앱 시작·포그라운드 복귀 | S1 기능 맵 확인 (B02) |
| 외부 OS | 권한 결과, 공유 시트 결과, 오버레이 권한 철회 | DENY, N01-04 |

**안내 흐름 = 단계 시퀀스** (내 분류의 「단계 시퀀스」 그대로)

- `FlowState`(enum): `IDLE → PICKED → ANALYZING → IDENTIFIED → GUIDING(n) → DONE`, 예외 `DENIED`, `ERROR(code)`, `CANCELLED`
- **Runner**: 상태에 들어갈 때 할 일 (`ANALYZING` 진입 = 분석 요청 + 3초 타이머 시작, `DONE` 진입 = 기록 저장)
- **Gate(전이 검사자)**: 허용된 전이만 통과. 예) `ANALYZING` 중 `analyze.run` 재요청 거부, `GUIDING`에서만 `guide.next`

```
IDLE ─pick→ PICKED ─analyze.run→ ANALYZING ─ok→ IDENTIFIED ─guide.start→ GUIDING(1..n) ─last→ DONE
  │            │                    ├─cancel→ CANCELLED → IDLE
  └─deny→ DENIED                    └─fail→ ERROR(code) ─retry→ PICKED / gallery→ IDLE
GUIDING ─"화면이 달라요"→ PICKED (재촬영)
```

**실패 분리**: 분기는 `if` 대신 타입으로. `sealed class AnalysisOutcome { Success, Failure(code: ErrorCode) }`, `ErrorCode` = `NO_PATH`, `IMAGE_READ_FAILED`, `ANALYSIS_FAILED`, `UNKNOWN_SCREEN`, `NO_TARGET`, `TIMEOUT`. E 화면은 `ErrorCode`별 문구·복구 버튼만 고른다.

**생애주기**: 앱 시작 → 로컬 기능 맵 로드(없으면 내장 샘플) → 백그라운드 B02 확인(다운로드 → 해시·서명·스키마 검증 → 원자 교체, 실패 시 이전 맵 유지).

### 1.6 규모: 클래스·객체 (디자인 패턴, MICRO)

패턴을 먼저 고르지 않고, **바뀌는 지점**에서만 쓴다.

| 바뀌는 지점 | 패턴 | 위치 |
|---|---|---|
| 개인정보 종류가 늘어난다 (주민번호, 전화, 계좌…) | **Strategy** `PiiDetector` × N (정규식별·ML Kit 개체) | Kotlin Privacy |
| 안내 상태마다 가능한 행동이 다르다 | **State** (`FlowState` + Gate) | Flutter Guide |
| 버튼마다 하는 일이 다르다 | **Command** = 기능 ID → 핸들러 | 2.5 |
| 분석 단계를 끼우고 빼고 싶다 | **파이프라인(Template Method/체인)** `AnalysisStage` | Kotlin Analysis |
| 실제/가짜 구현을 바꿔 끼운다 | 인터페이스 + **생성자 주입**, 조립은 `bootstrap()` 한 곳 | 양쪽 |
| 상태가 바뀌면 화면이 따라 바뀐다 | **Observer** (`Stream`/`ValueNotifier`) | Flutter C → V |
| 안내 렌더러가 둘 (앱 화면, 오버레이) | **같은 계약, 다른 렌더러** | Guide / Overlay |

클래스 크기 기준: 40줄 안팎, 100줄을 넘으면 사용 주체·수직 층·사이클이 섞였는지 보고 나눈다. (지금 `GuideLogic.kt`는 `ScreenIdentifier`, `TargetFinder`, `PiiDetector` 셋으로 나눌 후보)

### 1.7 핵심 로직 (자료구조·알고리즘·불변식)

| 로직 | 무엇을 기억 | 판단 기준 | 불변식 |
|---|---|---|---|
| 화면 식별 `identifyScreen` | 기능 맵의 화면별 앵커 목록 | 정규화한 라벨에 앵커가 모두 있는 화면 1개 | 후보 0개·2개 이상이면 식별 실패(추측 금지) |
| 대상 찾기 `findTarget` | `UiElement` 목록 | 정확 일치 → 편집거리 1 허용, 후보 1개일 때만 | 짧은 라벨·한 글자 선택자는 오매칭 방지 |
| 개인정보 검출 | 정규식 + 개체 추출 결과 | 숫자 앞뒤가 숫자가 아님 `(?<!\d)…(?!\d)` (`\b` 사용 금지, 3.2 결함) | 겹치는 후보는 병합, 같은 범위는 1개 |
| 기능 맵 교체 | 현재·새 버전 | 검증 3종 통과 시에만 교체 | 교체는 원자적, 실패 시 이전 맵 유지 |
| 데이터 경계 | — | — | 원본·OCR 원문은 Kotlin 모듈 밖으로 나가지 않는다 |

## 2. 프론트로직 — 보이는 동작에서 기능으로 (5계층)

### 2.1 렌더러 — 셸과 셀

**셸(Shell)**: 화면들을 담는 틀. 이동·전역 상태 표시만 하고 업무 판단은 안 한다.

| 셸 | 담는 화면 | 하는 일 |
|---|---|---|
| `AppShell` | H, HISTORY, SETTINGS | 상단 바, 글자 크기 적용, 전역 오류 배너 |
| `GuideShell` | CP·C·CR / G·GS·GR / CA·GA / RC·RG / D1~D5 / DONE / E | 전체 화면, 단계 표시줄, 취소 버튼 |
| `ShareShell` | P, SHARE | 가림 확인 → 공유 |
| `OverlayShell` (Kotlin) | LP, L·LO, LT·LX, LG1~LG5 | 다른 앱 위 창. **Guide와 같은 `GuideStep` 계약을 그린다** |

**셀(Cell)**: 셸 안의 최소 표시 단위. 상태를 받아 그리기만 하고, 누르면 기능 ID만 올려 보낸다. 모두 `Tid` 이름표를 단다.

`BigActionButton`, `GuideCard`, `HighlightBox`, `StepBar`, `PiiChip`, `ErrorPanel`, `ImagePreview`, `HistoryTile`

규칙: 셀은 판단 0·쓰기 0. 로딩·성공·실패는 화면 상태에서 받은 값으로만 그린다.

### 2.2 계약 — 4종

**① 화면 계약** (화면 1장 = 받는 상태 + 낼 수 있는 행동)

| 화면 | 받는 상태 | 가능한 행동(기능 ID) |
|---|---|---|
| H 홈 | 최근 기록 3개, 맵 버전 | `capture.camera`, `capture.gallery`, `history.open` |
| CA/GA 분석 중 | 경과 시간, 취소 가능 여부 | `analyze.cancel` |
| RC/RG 식별 결과 | 화면 이름, 기능 목록 | `guide.start(featureId)`, `capture.retake` |
| D1~D5 안내 단계 | 단계 번호·총수, 강조 위치, 안내 문구 | `guide.next`, `guide.prev`, `guide.mismatch` |
| DONE | 요약 | `share.prepare`, `home` |
| P 공유 전 확인 | 후보 목록·가림 여부 | `privacy.toggle(id)`, `share.send` |
| E 오류 | `ErrorCode`, 복구 행동 목록 | `capture.retake`, `capture.gallery`, `home` |
| DENY | 거부된 권한 | `capture.gallery`, `settings.openPermission` |

**② 흐름 계약** (단계 kind: ask / wait / confirm / complete)

| 흐름 | 단계 |
|---|---|
| 안내 흐름 | 입력 선택(ask) → 분석(wait) → 식별 확인(confirm) → 안내 단계 1..n(ask) → 완료(complete) |
| 공유 흐름 | 후보 확인(confirm) → 공유 시트(wait) → 완료(complete) |
| 기능 맵 갱신 | 확인(wait) → 검증(wait) → 교체(complete) — 사람 단계 없음 |
| 오버레이 흐름 | 권한 확인(confirm) → 표시(ask) → 종료(complete) |

**③ 기능 계약** (기능 ID = capability 1개, 입력 → 출력)

| 기능 ID | 입력 | 출력 | 처리 모듈 |
|---|---|---|---|
| `capture.camera` / `capture.gallery` | — | 이미지 경로 / `DENIED` / 취소 | Capture |
| `analyze.run` | 이미지 경로 | `AnalysisOutcome` | Analysis (채널) |
| `analyze.cancel` | — | `CANCELLED` | Analysis |
| `guide.start` / `next` / `prev` / `mismatch` | 기능 ID / — | 다음 `GuideStep` | Guide |
| `privacy.toggle` | 후보 ID | 갱신된 후보 목록 | Privacy |
| `share.send` | 가린 이미지 | 공유 결과 | Share |
| `history.list` / `history.open` | — / 기록 ID | 목록 / 세션 | History |
| `map.check` | — | 맵 버전 | FeatureMap |
| `overlay.start` / `stop` | `GuideStep` | 표시 여부 | Overlay |

**④ 클래스 계약** (구현을 바꿔 끼우는 경계 = 인터페이스)

### 2.3 조립기·등록부

- **`bootstrap(env)`**: 실제/가짜 구현을 생성해 주입하는 유일한 곳 (Composition Root). 앱은 `bootstrap(prod)`, 시험은 `bootstrap(test)`.
- **`ActionRegistry`**: `Map<ActionId, Handler>`. 시작할 때 모든 화면 계약의 행동이 핸들러를 가졌는지 검사 → 빠진 연결은 실행 전에 발견. 이 검사 자체를 flutter_test 1건으로 둔다.
- **라우트 표**: 화면 ID(H, CA, RC, D1…) ↔ 위젯. UI 설계서 화면 ID를 그대로 쓴다.
- Kotlin: `MainActivity`가 채널 이름 ↔ 핸들러를 등록 (`screen_guide/analyze`, `screen_guide/overlay`).

### 2.4 런타임·관문

| 관문 | 검사 | 실패 시 |
|---|---|---|
| 흐름 Gate | 지금 상태에서 허용된 기능 ID인가 | 무시 + 로그 |
| 권한 | 카메라/오버레이 권한 | DENY 화면 |
| 중복 실행 | 분석 진행 중 재요청 | 거부 |
| 시간 제한 | 분석 3초 초과 | `ERROR(TIMEOUT)` |
| 취소 | 취소 토큰 | `CANCELLED`, Kotlin 코루틴 취소 |
| 기능 맵 | 로드된 맵 존재 | 내장 샘플 맵 사용 |

### 2.5 기능 (UseHandle)

버튼 → 기능 ID → `ActionRegistry` → 핸들러 → 유스케이스. 버튼 안에는 로직이 없다.

```dart
// 셀: 누르면 ID만 올린다
BigActionButton(tid: 'btn_gallery', label: '갤러리에서 선택', action: ActionId.captureGallery)

// 런타임: Gate 통과 후 핸들러 실행
void dispatch(ActionId id, [Object? arg]) {
  if (!sequence.allows(id)) return;
  registry[id]!.handle(arg);
}
```

## 3. 두 관점 연결표

| 사용자 동작·기대 결과 | 화면·흐름 계약 | 기능 ID·핸들러 | 담당 유스케이스·모듈 | 상태 소유자·변경 규칙 | 반환 결과·화면 반영 |
|---|---|---|---|---|---|
| A1 갤러리에서 사진을 고른다 | H → 안내 흐름 ask | `capture.gallery` → `GalleryHandler` | Capture `PickImage` | `GuideSessionController`: `IDLE→PICKED` | 경로 / 취소면 그대로 H |
| A2 분석을 시작해 화면이 식별된다 | CA wait → RC confirm | `analyze.run` → `AnalyzeHandler` | Analysis `AnalysisCoordinator`(Kotlin) | `PICKED→ANALYZING→IDENTIFIED`, 실패 시 `ERROR(code)` | `AnalysisOutcome` → RC 또는 E |
| A3 다음 단계를 누른다 | D(n) ask | `guide.next` → `GuideStepHandler` | Guide `AdvanceStep` | `GUIDING(n)→n+1`, 마지막이면 `DONE` + 기록 저장 | 다음 `GuideStep` → 강조 갱신 (오버레이도 같은 계약) |
| A4 가린 뒤 공유한다 | P confirm → SHARE wait | `privacy.toggle`, `share.send` | Privacy `MaskImage` → Share | 후보 확인 여부는 Privacy 소유 | 가린 이미지 → 공유 시트 |
| S1 앱 시작 시 맵을 갱신한다 | 기능 맵 흐름 (사람 없음) | `map.check` → `MapUpdateHandler` | FeatureMap `UpdateFeatureMap` | `FeatureMapRepository`: 검증 통과 시 원자 교체 | 맵 버전 → H 표시 |

읽기 길: 화면 → 화면 계약 → 조회 기능(`history.list`) → `HistoryRepository` → 응답 → 셀 표시.
쓰기 길: 버튼 → 기능 ID → Gate → 핸들러 → 유스케이스(규칙·상태 변경) → 상태 Stream → 화면 갱신.

## 6. 만드는 순서 (얇게 연결 → 채우기)

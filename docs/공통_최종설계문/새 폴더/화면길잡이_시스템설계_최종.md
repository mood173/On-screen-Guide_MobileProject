# 화면길잡이 시스템 설계 (최종)

2026-11-11 · 강민준 작성
기준: 러프 설계(`설계_러프_보완`, `전체설계_러프`), 개발 계약 v1, 골격 코드 `feat/skeleton` 커밋 `ccd7f84`, 형주 세부계획(`collaboration_plan`), 정혁 협업 계약, 미니프로젝트 #2107 안내

> 이 문서가 답하는 것: **앱이 어떤 단계로 돌아가고, 단계마다 시스템이 무엇을 준비하고, 그때 화면은 어떤 틀로 무엇을 보여 주는가.**
> 화면 33개를 나열하지 않고, 실행 흐름 단계 8개를 뼈대로 두고 화면은 그 단계의 한 장면으로 배치한다.
> 누가 무엇을 만드는지는 다음 문서(시스템 역할 설계)에서 다룬다.
> **[11/11 갱신]** 기능별로 코드와 대조한 결론이 `화면길잡이_기능별_검토_결론.md`에 있다. 그 결론을 이 문서 본문에도 반영했다. 근거와 세부, 제외·보류 기록(13장)은 그 문서를 본다.

## 1. 출발점

### 1-1. 한 문장

**"안내받고 싶은 앱 화면을 찍거나 고르면, 기기 안에서 그 화면을 알아보고, 원하는 기능까지 누를 곳을 단계별로 짚어 주고, 공유하기 전에는 개인정보 후보를 알려 준다."**

### 1-2. 변하지 않는 것과 변하는 것 (러프 설계 0장)

| 변하지 않는 핵심 | 설계상 자리 |
|---|---|
| ① 사진 속 글자와 위치를 알아본다 | Kotlin 분석 모듈 (OCR → `UiElement`) |
| ② 앱마다의 화면·기능·단계 정보가 있다 | 기능 맵 (`GuidanceRepository`) |
| ③ ①과 ②를 대조해 화면을 식별하고 누를 곳을 찾는다 | Kotlin 규칙 (`identifyScreen`, `findTarget`) |
| ④ 민감한 내용은 기기 밖으로 나가지 않고, 공유 전에 알린다 | 개인정보 보호축 (검출 = Kotlin, 확인 관문 = 흐름) |

| 변하는 것 | 감추는 인터페이스 |
|---|---|
| 입력 방식 (갤러리 / 카메라 / 실시간) | `GalleryInput`, `CameraInput` |
| 인식·판단 방법 (ML Kit → 다른 모델) | `ScreenAnalyzer` (채널 뒤) |
| 지원 앱·기능 데이터 | `GuidanceRepository`, `MapUpdater` |
| 저장·공유 기술 | `HistoryRepository`, `Sharer` |
| 기기 화면 비율 | 좌표 변환 함수 (구현이 하나라 인터페이스는 두지 않는다) |
| 표시 방식 (앱 안 화면 / 다른 앱 위 오버레이) | 같은 `GuideStep`을 받는 렌더러 둘 |

### 1-3. 미니프로젝트 #2107 포괄

이 앱은 미니프로젝트 세 단계(사진 분석 앱)를 그대로 포함한다. 분석 기능은 "텍스트 인식"을 골랐다.

| 미니프로젝트 | 통과 기준 | 이 설계에서 채우는 곳 |
|---|---|---|
| **MP1** 카메라와 권한 | 카메라·갤러리 두 경로 입력 | 입력 단계 (3-3), `GalleryInput`·`CameraInput`. 갤러리는 앱 안 목록에서, 카메라는 기기 기본 카메라 앱으로 |
| | 권한 거부 시 크래시 없이 안내 화면 (설정 이동 포함) | 복구 단계의 DENY, `openAppSettings` (6-2) |
| | 선택 취소 등 예외에서 정상 동작 | `PickStatus` 4종 → 단계 전이 (3-3) |
| | 권한이 왜 필요한지 설명 | CP 화면 (카메라 접근 설명) |
| **MP2** 온디바이스 분석 | 입력 → 분석 결과 표시 | 분석·선택 단계 (3-4, 3-5) |
| | 비행기 모드에서도 분석 | 분석은 Kotlin + ML Kit 번들 모델, 네트워크 호출 없음 (5장) |
| | 인식 불가를 오류가 아닌 안내로 | `UNKNOWN_SCREEN` → 복구 단계 "다시 촬영해 주세요" |
| | 처리 시간 측정값 기록 | 응답의 `timingMs` (ocr, total) → README |
| **MP3** 이력과 공유 | 이력 저장·목록·삭제, 재시작 후 유지 | 마무리 단계 + 기록 (3-7, 3-9), `HistoryRepository` 로컬 DB |

| | 시스템 공유 시트로 전달 | 공유 단계 (3-8), `Sharer` |

미니프로젝트에 없는데 이 앱에 더 있는 것: 화면 식별과 단계 안내(기능 맵), 개인정보 후보 알림, 기능 맵 갱신, 실시간 오버레이.

## 2. 전체 구조

### 2-1. 규모별 결정

| 규모 | 결정 | 이유 |
|---|---|---|
| 시스템 | 기기 안에서 다 처리하는 한 개의 앱. 서버는 기능 맵 배포와 (동의 시) 이력 동기화 두 곳뿐 | 원본 이미지가 기기를 떠나지 않아야 한다 |
| 영역 | Flutter(화면·흐름·데이터) + Kotlin(분석). 둘 사이는 채널 하나 | ML Kit는 Android 쪽, 화면은 Flutter 쪽 |
| 분석 내부 | 순서대로 넘기는 처리 줄: 디코딩 → OCR → 요소 → 화면 식별 → 대상 찾기 → 개인정보 후보 → 병합 → 가림 값 | 단계마다 따로 시험할 수 있다 |
| 클래스 | 단계별 설정(State), 버튼 → 핸들러(Command), 개인정보 유형(Strategy), 상태 → 화면(Observer), 구현 교체(포트 + 생성자 주입) | 바뀌는 지점마다 하나씩 |

### 2-2. 층 (수직) — 골격 코드의 폴더와 대응

```
세부사항   lib/ui/ (위젯)   lib/data/ (플러그인·DB·채널 구현)   android/ (ML Kit, MainActivity)
   ↓ 안쪽으로만 의존
연결·번역  lib/contract/ (채널 JSON ↔ 자료형)   좌표 변환 함수   Kotlin 채널 코덱
   ↓
흐름·기능  lib/runtime/ (단계 관리, 관문, 버튼 등록부, 핸들러)   Kotlin 분석 순서 조정
   ↓
핵심       lib/core/ (ID·상태·오류 코드)   lib/domain/ (포트·모델)   Kotlin logic/ (규칙)
조립       lib/bootstrap.dart — 구현을 고르는 유일한 곳
```

### 2-3. 축 (수평)

| 축 | 하는 일 | 가진 상태 | 코드 위치 |
|---|---|---|---|
| 흐름 | 단계 전환, 관문, 버튼 처리 | 안내 세션 (현재 단계·이미지·결과·기능·단계 번호) | `lib/runtime/` |
| 분석 | 이미지 → 화면·요소·대상·개인정보 후보 | 없음 | `android/…/kotlin/` |
| 개인정보 보호 | 후보 검출·가림 값 / 공유 전 확인 | 확인 여부 | 검출 = Kotlin `logic/`, 관문 = `lib/runtime/` |
| 입력 | 사진 한 장 가져오기, 권한, 복사본 정리 | 고른 이미지 | `lib/data/` (`GalleryInput`·`CameraInput`·`InputCleanup` 구현) |
| 기능 맵 | 화면·기능·단계 조회, 갱신 | 활성 revision | `lib/data/` (`GuidanceRepository`, `MapUpdater` 구현) |
| 기록·공유 | 안내 기록 저장·조회, 텍스트 공유 | 기록 목록 | `lib/data/` (`HistoryRepository`, `Sharer` 구현) |
| 표시 | 셸·화면·셀, 테마 | 화면 전용 상태만 (접힘·포커스) | `lib/ui/` |

축끼리는 포트와 계약 자료형으로만 주고받는다. 개인정보 검출 코드는 화면 식별·기능 맵을 참조하지 않는다 (떼어서 다른 곳에 쓸 수 있게).

### 2-4. 폴더 구조 (확정: 기능별)

맨 위 폴더는 기능(수평), 기능 폴더 안은 층(수직)이다. 2-2·2-3·6장에 적힌 `lib/ui`, `lib/runtime`, `lib/data` 경로는 골격 `ccd7f84` 기준이고, 옮긴 뒤에는 아래 표로 읽는다.

```
lib/
  app/        bootstrap, 흐름 입구(GuideFlow), 단계 설정표, 버튼 등록부, 셸
  shared/     contracts/ (ActionId·ScreenId·ErrorCode·FlowState, 채널 자료형), cells/, theme/, coordinate_mapper
  features/
    capture/       domain(GalleryInput·CameraInput·InputCleanup)  data(구현)  ui(CP·CR·G·GS·GR)  handlers
    analyze/       domain(ScreenAnalyzer)  data(채널·가짜)  ui(CA·GA)  handlers
    guide/         ui(RC·RG·D1~D5·DONE·E)  handlers
    privacy/       ui(P)  공유 전 확인 관문 규칙
    share/         domain(Sharer)  data(구현)  ui(SHARE)  handlers
    history/       domain(HistoryRepository)  data(DB)  ui(HISTORY)  handlers
    guidance_map/  domain(GuidanceRepository·MapUpdater)  data(DB·Firebase)
    settings/      ui(SETTINGS·DENY)
```

| 골격 위치 | 옮긴 위치 |
|---|---|
| `lib/core/`, `lib/contract/` | `lib/shared/contracts/` |
| `lib/domain/*.dart` (포트) | 각 기능의 `domain/` |
| `lib/data/*` | 각 기능의 `data/` |
| `lib/runtime/guide_flow.dart` | `lib/app/` (입구·단계 설정표·등록부) + 각 기능의 `handlers/` |
| `lib/ui/screen/*` | 각 기능의 `ui/` |
| `lib/ui/cell/`, `lib/ui/theme/` | `lib/shared/cells/`, `lib/shared/theme/` |

의존 규칙: 기능 폴더 안에서 `ui`와 `data`는 `domain`만 본다. `ui`는 `data`를 보지 않는다. 기능끼리는 서로의 `domain`과 `shared/contracts`만 본다. `privacy`는 다른 기능을 보지 않는다. 구현을 만드는 곳은 `app/bootstrap`뿐이다. 포트 이름과 서명은 바뀌지 않는다.

## 3. 실행 흐름 단계 — 설계의 뼈대

### 3-0. 단계 한눈에

```
준비 ─▶ 대기 ─▶ 입력 ─▶ 분석 ─▶ 선택 ─▶ 안내 ─▶ 마무리
                 ▲        │        │        │         │
                 │        ▼        ▼        ▼         ▼
                 └────── 복구 ◀────┘     (화면이 달라요)  공유 ◀─ 기록에서도 진입
        대기 ◀──▶ 기록·설정
```

| 단계 | 사용자가 하는 일 | 세션 상태 (`FlowState`) | 화면 (`ScreenId`) |
|---|---|---|---|
| 준비 | (없음, 앱 시작) | — | 시작 화면 |
| 대기 | 무엇을 할지 고른다 | `idle` | H |
| 입력 | 화면을 찍거나 고른다 | `idle` → `picked` | CP·CR / G·GS·GR (C는 기기 기본 카메라가 대신한다) |
| 분석 | 기다린다 (취소 가능) | `analyzing` | CA / GA |
| 선택 | 결과를 보고 기능을 고른다 | `identified` | RC / RG |
| 안내 | 짚어 준 곳을 누르고 다음으로 | `guiding` | D1~D5 |
| 마무리 | 저장하거나 끝낸다 | `done` | DONE |
| 공유 | 개인정보 후보를 확인하고 보낸다 | (세션 유지) | P → SHARE |
| 복구 | 다시 시도할 방법을 고른다 | `denied` / `error` | DENY / E |
| 기록·설정 | 지난 안내를 보거나 설정한다 | `idle` | HISTORY / SETTINGS |

**단계와 화면의 관계**: 단계는 "사용자가 지금 하는 일"이고, 화면은 그 단계 안의 한 장면이다. CR과 GR, CA와 GA, RC와 RG는 입력 방식만 다른 같은 장면이라 **화면 위젯은 하나, 입력 방식만 인자로 받는다** (골격의 `ReviewScreen`, `AnalyzingScreen`, `ResultScreen`이 이미 그렇게 되어 있다). D1~D5도 `GuideStepScreen` 하나다.

### 3-1. 단계가 정하는 것 (단계 설정표)

단계에 들어갈 때 시스템이 아래 다섯 가지를 한 번에 정한다. 화면 위젯이 각자 정하지 않는다.

| 정하는 것 | 뜻 |
|---|---|
| 들어갈 때 준비 | 미리 불러 둘 것, 시작할 일 |
| 화면 틀 | 어느 셸, 진행 표시 몇 번째, 뒤로 가기가 어디로 가는지 |
| 허용 버튼 (관문) | 이 단계에서 눌러도 되는 `ActionId` |
| 쓰는 포트 | 이 단계가 부르는 인터페이스 |
| 나갈 때 정리 | 지울 것, 멈출 것 |

### 3-2. 준비 · 대기

| | 준비 | 대기 |
|---|---|---|
| 들어갈 때 | `bootstrap()`으로 구현 조립 → 버튼 등록부 검사 → `MapUpdater.checkForUpdate()`를 **기다리지 않고** 시작 | 세션 비우기, 남은 앱 복사본 삭제 |
| 화면 틀 | 시작 화면 | 앱 셸 (하단 탭: 홈·기록·설정), 진행 표시 없음 |
| 허용 버튼 | 없음 | `captureGallery`, `captureCamera`, `overlaySetup`, `navHistory`, `navSettings` |
| 쓰는 포트 | `MapUpdater`, `GuidanceRepository` | `HistoryRepository.list` (최근 기록 3건) |
| 실패 | 맵 갱신 실패 → 이전 revision으로 계속. 맵이 아예 없으면 내장 맵 | — |

### 3-3. 입력

| 항목 | 내용 |
|---|---|
| 들어갈 때 | 입력 방식(갤러리 / 카메라)을 세션에 기록. 카메라는 권한 설명 화면(CP)부터, 갤러리는 사진 접근 권한을 확인한 뒤 최근 사진·스크린샷 목록(G)을 그린다 |
| 화면 틀 | 안내 셸, 진행 표시 1/5 "입력", 뒤로 = 대기 |
| 허용 버튼 | `captureGallery`, `captureCamera`, `capturePick(id)`, `captureConfirm`, `captureRetake`, `analyzeRun`(이미지가 있을 때만) |
| 쓰는 포트 | 갤러리: `GalleryInput.requestAccess` → `recent`(최근 9장) → `use` / 카메라: `CameraInput.takePhoto` |
| 결과에 따른 전이 | `ok` → 확인 장면(CR/GR), 상태 `picked` / `cancelled` → 그 자리 유지 / `permissionDenied` → 복구(DENY) / `readFailed` → 복구(E, `IMAGE_READ_FAILED`) |
| 나갈 때 | 다시 고르면 앞 이미지의 앱 복사본 삭제 (`InputCleanup.release`) |
| 불변식 | 이미지는 한 장. 위치·연락처 권한을 요청하지 않는다. 사용자 원본은 지우지 않는다 |

### 3-4. 분석

| 항목 | 내용 |
|---|---|
| 들어갈 때 | 요청 번호 발급 → `GuidanceRepository.fragment()`로 맵 조각 → `ScreenAnalyzer.analyze` 호출, 3초 타이머 시작 |
| 화면 틀 | 안내 셸, 진행 표시 2/5 "분석", 뒤로 = 취소 |
| 허용 버튼 | `analyzeCancel` 하나. 다시 요청은 받지 않는다 (중복 분석 차단) |
| 진행 표시 | 체크 3개는 연출이다 (채널이 응답을 한 번만 돌려준다). 3초를 넘으면 "조금 더 걸리고 있어요 · 계속 기다리기 / 취소" |
| 결과에 따른 전이 | 성공 + 화면 식별 → 선택 / `screenId` 없음 → 복구(`UNKNOWN_SCREEN`) / 오류 → 복구(코드 그대로) / 취소 → 입력의 확인 장면 |
| 취소 처리 | 요청 번호를 버린다. 늦게 온 응답은 무시한다 |
| 나갈 때 | 타이머 정지 |

### 3-5. 선택

| 항목 | 내용 |
|---|---|
| 들어갈 때 | `GuidanceRepository.actionsFor(screenId)`로 기능 목록. 응답의 `pii[]`를 세션에 보관 |
| 화면 틀 | 안내 셸, 진행 표시 3/5 "기능 선택". 이미지 위에 인식 요소 상자, 개인정보 후보가 있으면 경고 띠 |
| 허용 버튼 | `guideStart(기능)`, `captureRetake`. 공유와 저장은 이 단계에서 열지 않는다 (공유할 사용 방법이 아직 없다) |
| 쓰는 포트 | `GuidanceRepository` |
| 전이 | 기능 고름 → 안내 / 다시 → 입력 |
| 기능이 0개 | 화면은 알아봤지만 안내할 기능이 없음 → "이 화면에서 안내할 수 있는 기능이 아직 없어요" + 다시 고르기 |

### 3-6. 안내

| 항목 | 내용 |
|---|---|
| 들어갈 때 | 단계 n의 선택자로 `ScreenAnalyzer.analyze(target 포함)` → 대상 위치 |
| 화면 틀 | 안내 셸, 진행 표시 4/5 "안내", 단계 n/N 표시. 이미지 위에 강조 테두리, 아래에 안내 카드(할 일 + 누르면 일어나는 일) |
| 허용 버튼 | `guideNext`, `guidePrev`, `guideMismatch`. 대상을 찾는 중에는 셋 다 잠근다 |
| 전이 | 다음 → n+1 또는 마무리 / 이전 → n−1 또는 선택 / 대상 없음 → 복구(`NO_TARGET`) |
| 다른 화면의 단계 | 단계의 화면이 지금 이미지의 화면과 다르면 이미지 없이 글 안내 카드로 보여 준다. 오류가 아니다 |
| 화면이 달라요 · 화면 올려서 짚어 보기 | 기능을 유지한 채 **입력만 다시** 받고, 올린 화면의 ID로 그 화면에 해당하는 단계를 찾아 이동한다 (기능별 검토 결론 4-2). 세션이 입력 방식을 기억한다 |
| 표시 규칙 | 흐름은 "몇 단계, 어디, 무슨 의미(진행 중 / 완료 / 개인정보)"만 넘긴다. 색·움직임은 화면이 정한다. 흐름은 애니메이션이 끝나기를 기다리지 않는다 |

| 항목 | 내용 |

| 들어갈 때 | 요약 만들기 (기능 제목, 단계 문구 목록) |

### 3-8. 공유

| 항목 | 내용 |
|---|---|
| 들어오는 곳 | 마무리, 기록 — 두 곳 모두 같은 단계로 들어온다 |

### 3-9. 복구 · 기록·설정

| | 복구 | 기록·설정 |
|---|---|---|
| 들어오는 곳 | 어느 단계에서든 실패했을 때. **어디서 왔는지 기억한다** | 대기의 하단 탭 |
| 화면 틀 | 안내 셸, 진행 표시는 실패한 단계에 멈춤 | 앱 셸 |
| 장면 | DENY(권한 설명 + 설정 열기 + 갤러리로 대신하기), E(코드별 문구 + 복구 버튼) | HISTORY(목록·다시 보기·삭제·공유), SETTINGS(권한 상태, 맵 revision, 동기화 동의) |

## 4. 화면 구조 — 단계가 틀을 정하고, 화면은 내용만 채운다

### 4-1. 셸 (틀) 4개

| 셸 | 쓰는 단계 | 고정된 틀 |
|---|---|---|
| 앱 셸 | 대기, 기록·설정 | 제목 + 본문 + 하단 탭 3개 |
| 안내 셸 | 입력 ~ 마무리, 복구 | 툴바(‹ 제목) + **진행 표시 5칸** + 본문 + 하단 버튼 영역. 골격의 `GuideScaffold` |
| 공유 셸 | 공유 | 툴바 + 본문 + 하단 버튼. 진행 표시 없음 |
| 오버레이 셸 (확장) | 실시간 안내 | Kotlin이 다른 앱 위에 그리는 테두리와 카드 |

진행 표시(입력 → 분석 → 기능 선택 → 안내 → 완료)는 UI 설계서(PDF) 각 화면 아래에 있다. Figma v2에서 빠졌을 뿐이므로 넣는다. 단계 구조를 쓰면 현재 칸 값이 저절로 나온다.

### 4-2. 셀 (부품)

| 셀 | 받는 값 | 내보내는 것 |
|---|---|---|
| 큰 버튼 | 문구, 허용 여부 | `ActionId` |
| 이미지 + 상자 (`ScreenImage`) | 이미지 경로, 상자 목록, 강조 의미 | — |
| 안내 카드 | 할 일, 다음에 일어나는 일 | — |
| 진행 표시 | 현재 칸, 단계 n/N | — |
| 기능 목록 줄 | 기능 제목·설명 | `guideStart(기능)` |
| 개인정보 후보 줄 | 유형, 가린 값 | — |
| 오류 패널 | `ErrorCode` | 복구 `ActionId` |
| 기록 줄 | 제목, 시각 | `historyOpen(id)` |

규칙 세 가지.
1. 셀과 화면은 값을 받아 그리기만 한다. 버튼은 `flow.dispatch(ActionId)`만 부른다.
2. 버튼의 켜짐·꺼짐은 관문(`flow.allows(id)`)이 정한다. 화면이 따로 판단하지 않는다.
3. 업무 상태(현재 단계, 분석 결과)는 위젯 안에 두지 않는다. 위젯에는 접힘·포커스 같은 화면 전용 상태만 둔다.

### 4-3. 화면 하나를 만들 때 확인하는 다섯 가지 (러프 설계 6.1)

어느 단계의 장면인가 → 어떤 값을 받고 어떤 `ActionId`를 내보내나 → 그 ID가 등록부에 있나 → 이 단계에서 허용되나 → 어느 핸들러가 처리하나. 빈 칸이 있으면 설계가 덜 된 것이다.

## 5. 분석 모듈 (Kotlin)

### 5-1. 처리 순서

```
imagePath ─▶ 디코딩 ─▶ OCR(ML Kit 한국어) ─▶ 요소 정리 ─┬▶ 화면 식별(요청의 앵커) ─▶ 대상 찾기(요청의 선택자)
                                                        └▶ 개인정보: 개체 추출 + 정규식 ─▶ 병합 ─▶ 가림 값
                                                                                    ─▶ 계약 JSON 응답
```

| 규칙 | 내용 |
|---|---|
| 화면 식별 | 요청으로 받은 화면별 앵커 중 2개 이상이 보이면 그 화면 |
| 대상 찾기 | 정확히 일치 → 없으면 길이가 같고 한 글자만 다른 후보가 하나일 때만. 한 글자짜리 선택자는 오인식을 허용하지 않는다 |
| 개인정보 | 개체 추출(전화·이메일·주소·카드·URL) + 정규식(등록번호·휴대·유선·계좌) → 겹침 합침, 한국 형식 우선, 날짜 제외 → 앞 3자·뒤 2자만 남김 |
| 상태 | 없음. 요청 하나 = 이미지 하나 = 응답 하나 |
| 네트워크 | 사용자 이미지와 글자는 나가지 않는다. OCR 모델은 앱에 들어 있어 비행기 모드에서 동작한다. 개체 추출 모델은 첫 실행 때 내려받고, 못 받으면 정규식만으로 진행한다 |

### 5-2. 지금 코드와 목표

| 항목 | 지금 (`ccd7f84`) | 목표 |
|---|---|---|
| 채널 인자 | `path`, `selector` (시험 앱 방식) | `requestId`, `imagePath`, `guidance`, `target` (계약 v1) |
| 화면 식별에 쓰는 맵 | Kotlin 안의 고정 `SAMPLE_MAPS` | 요청으로 받은 `guidance.screens` |
| 응답 | 시험 앱 형식 | 계약 v1 JSON. `contract_fixtures/analyze/`와 같은 키·타입 |
| 로그 | OCR 줄과 가린 값을 Logcat에 출력 | 줄 내용은 출력하지 않는다 (개수·시간만) |
| 정규식 | `\b` 경계 결함 | 숫자 경계 조건으로 교체 |
| 구조 | `MainActivity` → `Analyzer`(ML Kit + 순서) → `logic/GuideLogic`(규칙) | 규칙은 그대로. `Analyzer`에서 채널 변환을 떼어 `ChannelCodec`으로 (JUnit으로 예시 파일 대조 가능하게) |

`logic/`은 Android에 의존하지 않는 순수 함수라 JUnit 28건으로 지킨다. 포트(`VisionRecognizer`, `PiiDetector`)로 더 나누는 일은 선택이다.

## 6. 흐름 모듈 — 골격을 어떻게 넓히나

### 6-1. 지금 골격의 상태

`GuideFlow` 한 클래스(393줄)가 현재 화면, 관문 표, 버튼 처리(`switch`), 분석 요청, 세션 값을 모두 들고 있다. 갤러리 흐름 하나에는 충분했지만, 카메라·공유·기록·복구가 붙으면 한 파일에 모든 사람의 수정이 몰린다. 또 `runtime/`이 `data/`의 구현(`DemoGuidanceRepository`, `FakeImageInput`, `SampleImage`)을 직접 import하고 있어 "흐름은 포트만 안다"는 규칙이 코드에서는 깨져 있다.

### 6-2. 넓힌 구조

화면이 쓰는 입구(`flow.dispatch`, `flow.allows`, `ListenableBuilder`)는 그대로 둔다. 안쪽만 나눈다.

```
화면 ──dispatch(ActionId)──▶ GuideFlow (입구, ChangeNotifier)
                               │ ① 관문: 지금 단계·장면에서 허용되나      ← StageTable (단계 설정표)
                               │ ② 등록부: 이 ID의 핸들러                 ← ActionRegistry
                               ▼
                             Handler (기능별 작은 클래스) ──▶ 포트
                               │ 결과를 세션에 반영, 단계 전이 요청
                               ▼
                             GuideSession (세션 값, 바꾸는 곳은 흐름뿐)
                               │ 단계가 바뀌면
                               ▼
                             StageTable.onEnter / onExit (준비·정리)
```

| 부품 | 책임 | 러프 설계의 이름 |
|---|---|---|
| `Stage` (enum) + `ScreenId.stage` | 화면이 어느 단계에 속하는지 | 앱 모드 |
| `StageTable` | 3장의 단계 설정표를 코드로: 허용 버튼, 화면 틀 정보(셸·진행 칸), 들어갈 때·나갈 때 할 일 | `AppModeManager` + Gate |
| `ActionRegistry` | `ActionId` → `Handler`. 시작할 때 "모든 ID에 핸들러가 있거나 '준비 중'으로 명시됐는가" 검사 | 3층 등록부 |
| `Handler` 묶음 | 입력 / 분석 / 안내 / 기록 / 공유 / 이동. 핸들러는 포트를 생성자로 받는다 | 5층 기능 |
| `GuideSession` | 입력 방식, 이미지, 분석 결과, 기능, 단계 번호, 대상, 개인정보 후보, 오류, 들어온 단계 | `GuideSession` |
| `GuideFlow` | 위 넷을 묶는 입구. 관문 통과 → 핸들러 실행 → 알림 | 4층 런타임 |

### 6-3. 포트 최종 (골격 이름 유지, 보완만)

| 포트 | 골격 그대로 | 보완 | 보완 이유 |
|---|---|---|---|
| `ScreenAnalyzer` | `analyze(AnalyzeRequest)` | 없음 | — |
| `ImageInput` | `pickFromGallery`, `takePhoto`, `release` | 쓰는 쪽 기준으로 셋으로 나눈다: `GalleryInput`(`requestAccess`, `recent`, `use`), `CameraInput`(`takePhoto`), `InputCleanup`(`release`, `clearLeftovers`, `openAppSettings`) | 갤러리 장면·카메라 장면·정리가 서로의 메서드를 볼 필요가 없고, 카메라와 갤러리를 따로 갈아 끼울 수 있어야 한다 |
| `GuidanceRepository` | `fragment()`, `actionsFor(screenId)`, `activeRevision()` | 서명은 그대로. 맵 조각은 지원하는 모든 앱의 화면을 담고 화면 ID는 `앱.화면`. `GuideStep`에 `screenId` 추가 | 스크린샷만으로는 어느 앱인지 알 수 없다. 단계가 다른 화면에 걸칠 수 있다 |
| `HistoryRepository` | `save`, `list`, `get`, `delete` | 없음. 모델은 골격의 `HistoryEntry`(단계 문구·개인정보 유형 포함) | 다시 보기와 공유에 단계 문구가 필요하다 |
| `Sharer` | `shareText(text)` → `bool` | 반환을 `sent / dismissed / failed` 셋으로 | 닫음과 실패를 구분해야 안내 문구가 달라진다 (정혁 문서 3.1) |
| `MapUpdater` | `checkForUpdate()` | 없음 | — |
| 좌표 변환 | `ScreenImage` 안에 비율 계산 (맞게 동작함) | 포트로 만들지 않는다. `shared/`의 순수 함수로 빼고 단위 시험을 붙인다 | 구현이 하나뿐인 계산에 인터페이스를 두면 쓰지 않는 추상화가 된다 |
| `ImageFiles` | 샘플 → 캐시 파일 | 체험용 입력 구현 안으로 넣고 포트에서 뺀다 | 흐름이 샘플 전용 자료형을 알 필요가 없다 |

정혁 문서의 `loadActive()`(맵 통째 반환)와 `FeatureMap` 자료형은 **데이터 구역 안쪽**에서 쓴다. 흐름은 지금처럼 조회 메서드만 본다. 채널 JSON 변환(`AnalysisCodec`)은 골격의 `lib/contract/analysis.dart`에 이미 있으므로 새로 만들지 않는다.

### 6-4. 골격에서 바꿀 것 (작은 순서대로)

| # | 바꿀 것 | 끝난 기준 |
|---|---|---|
| 1 | `runtime/`의 `data/` import 제거. 기본 구현은 `bootstrap`과 시험 코드가 넘긴다 | `lib/runtime` 아래에 `data/` import 0건 (시험 1건으로 확인) |
| 2 | 세션의 `picked: SampleImage` → `PickedImage`. 체험용 샘플은 `GalleryInput`의 한 구현으로. 화면은 `Image.file(path)`로 그린다 | 흐름과 화면이 `SampleImage`를 모른다 |
| 3 | `ScreenId.stage`와 `StageTable` 도입. 화면별 관문 표를 단계 설정표로 옮김 | 기존 흐름 시험 통과 |
| 4 | `switch` → `ActionRegistry` + 핸들러 | "모든 `ActionId`에 핸들러" 시험 통과 |
| 5 | 세션 값을 `GuideSession`으로 묶기 | 화면은 세션 값만 읽는다 |
| 6 | 단계 진입·이탈 처리 (복사본 삭제, 타이머 정지, 맵 확인) | 대기로 돌아오면 앱 복사본 0개 |
| 7 | 좌표 변환 함수 분리, `Sharer` 반환형, 입력 인터페이스 셋으로, 버튼 ID 5개 추가 | 좌표 단위 시험, 포트 공용 시험 |

### 10-1. 복사본 삭제 시점 검토 (미결 ⑦)

기존 문장: "분석이 끝나면(오류여도) 앱이 만든 촬영 복사본만 삭제" (기능·개념 정리 12.1 ⑨, 중간 보고서 AI 2.2).

| 근거 | 내용 |
|---|---|
| 코드 1 | 골격 `GuideFlow._locate()`는 **안내 단계마다** 같은 `_imagePath`로 `analyze(target 포함)`를 다시 부른다. 첫 분석 뒤에 지우면 1단계 안내부터 `IMAGE_READ_FAILED`가 난다 |
| 코드 2 | "이전 단계", "화면이 달라요"도 같은 경로로 다시 분석한다 |
| 화면 | 선택·안내 화면은 그 이미지를 배경으로 깔고 상자와 테두리를 그린다. 실제 사진은 에셋이 아니라 파일이므로 파일이 있어야 그릴 수 있다 |
| 원래 문장의 배경 | 중간 보고서의 시험 앱은 분석을 한 번 하고 결과만 보여 주는 구조였다. 그 구조에서는 "분석이 끝나면" = "이미지를 다 썼을 때"였다. 지금은 분석이 세션 동안 여러 번 일어나므로 같은 뜻을 지키려면 "그 이미지로 하는 마지막 분석이 끝났을 때" = 세션 종료가 된다 |

보관 시간이 늘어나는 데 따른 위험과 대응.

| 위험 | 대응 |
|---|---|
| 세션 도중 앱이 강제 종료되면 복사본이 남는다 | 준비 단계(앱 시작)에서 앱 임시 폴더의 `sg_` 복사본을 모두 지운다 |
| 오류 화면에서 오래 머문다 | 복구 단계에서 다시 고르거나 홈으로 가는 순간 지운다. "오류여도 지운다"는 원래 뜻은 그대로다 |
| 다른 앱이 읽을 수 있나 | 복사본은 앱 전용 임시 폴더에 있어 다른 앱이 읽지 못하고, 앱을 지우면 같이 지워진다 (골격 `CacheImageFiles` 주석, 11/6 에뮬레이터 확인) |

결론: 삭제 시점을 세션 종료로 바꾸고 시작 시 청소를 더한다. `기능·개념 정리` 12.1 ⑨와 `전체설계_러프` 1.3의 문장을 같이 고친다. 결합 점검표에 "홈으로 돌아온 뒤 임시 폴더에 복사본 0개"를 넣는다.

### 1-2. 인터페이스와 자료구조 (최종)

```dart
enum PickStatus { ok, cancelled, permissionDenied, readFailed }
enum InputKind { gallery, camera }            // 실시간이 붙으면 live 추가
enum GalleryKind { photo, screenshot }

class GalleryItem {            // 목록 한 칸. 화면이 그릴 때만 쓴다
  final String id;
  final Uint8List thumbnail;   // 작은 미리보기만
  final GalleryKind kind;
  final DateTime takenAt;
}
class PickedImage {            // 가져온 결과
  final PickStatus status;
  final String? path;          // 앱 복사본의 파일 경로 (ok일 때만)
  final InputKind input;
}

abstract interface class GalleryInput {       // 갤러리 장면만 본다
  Future<PickStatus> requestAccess();          // ok 또는 permissionDenied
  Future<List<GalleryItem>> recent({int limit = 9});
  Future<PickedImage> use(String id);
}
abstract interface class CameraInput {        // 카메라 장면만 본다
  Future<PickedImage> takePhoto();
}
abstract interface class InputCleanup {       // 흐름(세션 종료·앱 시작)과 권한 안내 화면이 본다
  Future<void> release(PickedImage image);
  Future<void> clearLeftovers();               // 앱 시작 때 남은 복사본 청소
  Future<void> openAppSettings();
}
```

### 2-1. 구조

| 항목 | 내용 | 판정 |
|---|---|---|
| 인터페이스 | `ScreenAnalyzer.analyze(AnalyzeRequest) → AnalysisResult` 하나 | 좋다. 쓰는 쪽이 채널·Kotlin·ML Kit를 모른다 |

| 응답 자료 | 화면 ID, 요소(글자 + 상자), 대상, 개인정보(유형 + 가린 값 + 요소 번호), 엔진 상태, 시간 | OCR 줄 전체와 후보 원문이 빠져 있다. 경계가 지켜졌다 |

### 2-2. 알고리즘 결함 (Kotlin `GuideLogic.kt`, 가짜 분석기도 같은 규칙을 복사해 쓰고 있음)

| # | 지금 동작 | 문제 | 결론 | 등급 |
|---|---|---|---|---|
| A | `identifyScreen`: 앵커가 줄 전체 **또는 줄 안의 단어 하나**와 같으면 인정, 2개 이상이면 그 화면 | 체험용 앵커가 `설정`, `알림 설정`이다. 화면에 "알림 설정" 한 줄만 있어도 `알림 설정`(줄 전체)과 `설정`(단어)이 둘 다 맞아 **한 줄로 2개가 채워진다** | 앵커 2개는 **서로 다른 요소**에서 맞아야 한다. 맵 공용 시험에 "앵커끼리 서로 포함하지 않는다"를 더한다 | 필수 |
| B | `identifyScreen`: 조건을 채운 **첫 번째** 화면을 고른다 | 두 화면이 모두 2개 이상 맞으면 맵에 적힌 순서로 결과가 정해진다 | 맞은 앵커 수가 **가장 많은 화면**. 같은 수면 식별하지 않는다(`screenId` 없음 → 다시 촬영 안내). 추정으로 고르지 않는다는 원칙과 같다 | 필수 |
| C | `findTarget`: 정확히 같은 요소 중 **첫 번째**를 고른다 | 계약은 "후보가 0개 또는 2개 이상이면 `target` 없음"이다. 같은 글자의 버튼이 두 개면 계약과 다르게 첫 번째를 짚는다 | 정확히 같은 요소가 **하나일 때만** 대상. 둘 이상이면 없음 | 필수 |
| D | `findTarget`: 줄 전체가 선택자와 같아야 한다 | OCR이 "홍길동 대화"처럼 여러 단어를 한 줄로 읽으면 선택자 `대화`를 못 찾는다 | 규칙은 그대로 둔다. 대신 기능 맵을 쓸 때 **실제 OCR 결과에서 한 줄로 읽히는 글자**만 선택자로 쓴다 (스크린샷 검증에서 확인) | 기록 |
| E | 정규식의 `\b` 경계 | 한글 옆의 숫자에서 경계가 안 잡힌다 (테스트 보고서 3.2) | 숫자 경계 조건으로 교체 (이미 할 일에 있음) | 필수 |

## 3. 선택 — 식별된 화면에서 기능 고르기

| 인터페이스 | `GuidanceRepository.actionsFor(screenId)` | 그대로 | — |

## 4. 안내 — 단계별로 누를 곳 짚기

### 4-1. 문제: 단계가 다른 화면으로 넘어갈 때

UI 설계서 11~15쪽의 예시는 "치킨 주문 5단계"이고, 단계마다 **다른 화면**이다(1단계 홈, 2단계 가게 목록 …). 그런데 입력은 정지 이미지 한 장이다(제약 C01).

지금 코드(`_locate`)는 모든 단계를 **처음 고른 한 장**에서 찾는다. 2단계의 대상은 그 이미지에 없으므로 `NO_TARGET` 오류 화면으로 간다. 체험용 기능 3개가 모두 한 화면 안에서 끝나서 드러나지 않았을 뿐이다.

문서에 있는 단서는 둘이다.
- 개발 계약 v1: "안내 단계마다 **새 사진**을 분석할 때는 그 단계의 선택자를 넣는다"
- UI 설계서: "화면이 달라요를 선택하면 현재 화면을 다시 스캔하고 같은 기능 ID의 새 UI 후보를 찾는다", "사용자가 실제 앱에서 직접 조작한다"

### 4-2. 결론 [확정 11/11 · 필수] — 글로 먼저 안내하고, 막히면 올리기

비교한 방법: (가) 단계마다 새 화면을 올려야 넘어감 → 앱을 여러 번 오가야 해서 무겁다. (나) 기능 맵에 예시 그림을 넣어 보여 줌 → 사용자의 실제 화면이 아니고, 다른 앱의 화면 그림을 배포·갱신해야 한다. **(다)를 택했다.**

1. 기능 맵의 단계마다 **그 단계를 하는 화면**을 적는다 (`GuideStep.screenId`). 골격의 `GuideStep`에는 이 칸이 없고, 정혁 문서의 `StepDef`에는 있다.
2. 단계 n에 들어갈 때:

| 경우 | 처리 |
|---|---|
| 단계의 화면 = 지금 이미지의 화면 | 그 이미지에서 대상을 찾아 테두리로 짚는다 |
| 단계의 화면 ≠ 지금 이미지의 화면 | 오류가 아니다. 이미지 없이 **글 안내 카드**(할 일 + 누르면 일어나는 일)를 보여 준다. 사용자는 실제 앱에서 읽고 따라간다. 버튼: [다음 단계], [이 화면 올려서 짚어 보기] |
| 화면은 같은데 대상을 못 찾음 | 복구 화면 (`NO_TARGET`) |

3. 사용자가 **막혔을 때만** 그 화면을 캡처해 올린다("이 화면 올려서 짚어 보기"와 "화면이 달라요"는 같은 길). 기능은 유지한 채 입력으로 가서 새 이미지를 받고, 분석해서 **올린 화면에 해당하는 단계로 맞춘다.**

```
올린 화면의 ID가 s, 지금 단계가 n일 때 (고른 기능의 단계 목록에서)
  ① n 이후(n 포함)에서 screenId == s 인 첫 단계 → 그 단계로 이동해 테두리로 짚는다
  ② 없으면 n 이전에서 screenId == s 인 마지막 단계 → 그 단계로 이동 (되돌아간 경우)
  ③ 그래도 없으면 → "이 기능의 화면이 아니에요" + [다시 올리기] / [기능 다시 고르기]
  화면을 식별하지 못했으면 → 복구 화면 (UNKNOWN_SCREEN)
```

4. 이 맞추기는 입력이 (단계 목록, 지금 단계 번호, 올린 화면 ID)이고 출력이 (단계 번호 또는 없음)인 **순수 함수**다. 단위 시험으로 ①②③을 각각 확인한다.
5. 새 이미지를 받으면 앞 이미지의 앱 복사본은 지운다. 한 번에 다루는 이미지는 여전히 한 장이다(제약 C01).
6. 실시간 오버레이는 3번의 "올리기"를 자동으로 하는 방식이다. 같은 맞추기 함수를 그대로 쓴다.

이렇게 하면 글 안내로 충분한 사용자는 다시 올리지 않아도 되고, 짚어 주는 것은 항상 사용자의 실제 화면이다. UI 설계서 D2~D5 그림(단계마다 다른 화면에 테두리)과 모습이 달라지는 점은 13장 X9에 기록했다.

| 분석 규칙 | 식별: 서로 다른 요소로 2개 이상 + 최다 일치, 같은 수면 미식별 / 대상: 정확 일치도 하나일 때만 | 민준 |
| 오류 전달 | 응답 본문의 `status`, 대문자 코드 | 민준 |
| 맵 공용 시험 | 앵커 포함 금지, 단계 5개 이하, 단계 화면 존재, 선택자 2자 이상 | 정혁 |
| 공유 | 결과 세 값, 들어오는 곳 두 곳 | 정혁 구현, 형주 흐름 |
| 좌표 변환 | 포트가 아니라 순수 함수, 형주 | 형주 |

## 12. 무드가 판단해 줄 것

대부분은 문서와 코드에 근거가 있어서 정했지만, 아래 둘은 제품 동작을 바꾸는 결정이라 확인이 필요하다.

1. ~~4장: 단계가 다른 화면으로 넘어갈 때의 처리~~ → **[확정 11/11] 글로 먼저 안내하고, 막히면 올려서 그 화면의 단계로 맞춘다** (4-2).
2. ~~3장·5장: 결과 화면의 "결과 저장 및 공유" 버튼~~ → **[확정 11/11] 이번에는 제외.** 이유와 다시 볼 조건은 13장에 기록.

## 1. 문서 정리 — 어느 문서가 무엇의 기준인가

형주 세부계획과 정혁 협업 계약이 같은 내용을 서로 다른 이름으로 적고 있어서, 겹치는 곳의 기준을 정한다.

| 주제 | 기준 | 다른 쪽 문서에서 바꿀 것 |
|---|---|---|
| 채널 JSON, `ActionId`, 오류 코드 | 개발 계약 v1 = 골격 `shared/contracts` | 없음 (둘 다 같다) |
| 포트 이름 | **골격 코드**: `Sharer`, `MapUpdater` 등. 사진 가져오기는 `GalleryInput`·`CameraInput`·`InputCleanup` 셋으로 나눔 | 정혁 문서의 `ImageSource`, `ShareGateway` → 코드 이름으로 |
| 사진 가져오기 결과 | 골격의 `PickedImage { status }` | 정혁 문서의 `sealed PickResult` → 쓰지 않음. 구분하는 네 가지 경우는 같다 |
| 기능 맵 조회 | 골격의 `fragment()`, `actionsFor()` | 정혁 문서의 `loadActive()`, `FeatureMap` → 데이터 구현 **안쪽**에서만 쓴다 |
| 채널 변환 (`AnalysisResult`, 코덱) | 골격에 이미 있음 (`contract/analysis.dart`) | 정혁 문서의 "누가 만드나"(남은 것 2) → 해결. 새로 만들지 않는다 |
| 공유 결과 | 정혁 문서: 보냄 / 닫음 / 실패 | 골격의 `Future<bool>` → 세 값으로 바꾼다 |
| 권한 설정 열기 | 정혁 문서: `openAppSettings` | 골격에 추가한다 (`InputCleanup`) |
| 좌표 변환 | 포트로 만들지 않는다. `shared/`의 순수 함수, 지형주 | 정혁 문서와 개발 계약 v1의 담당(데이터)을 고친다 |
| 폴더 구조 | **기능별** (시스템 설계 2-4, 정혁 문서와 같음) | 골격을 11/13 전에 한 번 옮긴다 |
| `bootstrap` 수정 | 골격 규칙: 각자 **자기 포트 줄만** | 정혁 문서의 "형주만 수정" → 골격 규칙으로 |
| 일정·결합 절차·점검표 | 형주 세부계획 | 이 문서 5장이 강의 일정에 맞춰 보완 |

## 4. 인터페이스 서명 — 최종안

골격 코드의 서명에 3장의 [제안]을 더한 모양이다. 11/13에 팀이 확인하면 계약 문서와 코드에 반영한다.

```dart
// ── 분석 (구현: 강민준 Kotlin + 채널 / 사용: 지형주) ── 변경 없음
abstract interface class ScreenAnalyzer {
  Future<AnalysisResult> analyze(AnalyzeRequest request);
}

// ── 사진 가져오기 (구현: 최정혁 / 사용: 지형주) ── 쓰는 쪽 기준으로 셋
enum PickStatus { ok, cancelled, permissionDenied, readFailed }
enum InputKind { gallery, camera }
enum GalleryKind { photo, screenshot }

class GalleryItem {            // 목록 한 칸
  final String id;
  final Uint8List thumbnail;   // 작은 미리보기만
  final GalleryKind kind;      // 저장 폴더 이름으로 판단 (관례)
  final DateTime takenAt;
}
class PickedImage {
  final PickStatus status;
  final String? path;          // 앱 임시 폴더의 복사본 경로 (ok일 때만)
  final InputKind input;
}

abstract interface class GalleryInput {
  Future<PickStatus> requestAccess();
  Future<List<GalleryItem>> recent({int limit = 9});
  Future<PickedImage> use(String id);
}
abstract interface class CameraInput {
  Future<PickedImage> takePhoto();             // 기기 기본 카메라 앱
}
abstract interface class InputCleanup {
  Future<void> release(PickedImage image);
  Future<void> clearLeftovers();               // 앱 시작 때
  Future<void> openAppSettings();
}

// ── 기능 맵 (구현: 최정혁 / 사용: 지형주, 간접적으로 강민준) ── 변경 없음
abstract interface class GuidanceRepository {
  Future<GuidanceFragment> fragment();
  Future<List<GuideAction>> actionsFor(String screenId);
  Future<String> activeRevision();
}

// ── 기록 (구현: 최정혁 / 사용: 지형주) ── 변경 없음
abstract interface class HistoryRepository {
  Future<void> save(HistoryEntry entry);
  Future<List<HistoryEntry>> list();        // 최근 것부터
  Future<HistoryEntry?> get(String id);
  Future<void> delete(String id);
}

// ── 공유 (구현: 최정혁 / 사용: 지형주) ──
enum ShareOutcome { sent, dismissed, failed }                       // [제안] bool → 세 값
abstract interface class Sharer {
  Future<ShareOutcome> shareText(String text);
}

// ── 기능 맵 갱신 (구현: 최정혁 / 사용: 지형주) ── 변경 없음
abstract interface class MapUpdater {
  Future<MapUpdateResult> checkForUpdate();
}

// 좌표 변환은 포트가 아니다. shared/ 의 순수 함수 (지형주)
```

골격의 `ImageInput`은 `GalleryInput`·`CameraInput`·`InputCleanup` 셋으로 나뉜다. `ImageFiles`(샘플 → 캐시 파일)는 체험용 구현 안으로 들어가고 포트에서 빠진다. `GuideStep`에는 `screenId`(그 단계를 하는 화면)가 추가된다.

### 흐름이 상태 값을 오류 코드로 바꾸는 표

| 포트 결과 | 흐름이 하는 일 |
|---|---|
| `PickStatus.cancelled` | 그 자리 유지 |
| `PickStatus.permissionDenied` | 복구 DENY (`PERMISSION_DENIED`) |
| `PickStatus.readFailed` | 복구 E (`IMAGE_READ_FAILED`) |
| 분석 응답 `status: error` | 복구 E (응답의 코드 그대로) |
| 분석 응답 `screenId` 없음 | 복구 E (`UNKNOWN_SCREEN`) |
| 분석 응답 `target` 없음 | 복구 E (`NO_TARGET`) |
| `ShareOutcome.dismissed` | 들어온 단계로 돌아감 |
| `ShareOutcome.failed` | "공유하지 못했어요" 안내 후 들어온 단계로 |
| `MapUpdateStatus.offline` / `rejected` | 아무것도 막지 않는다. 설정에 이전 revision 표시 |

## 7. AI 작업 기록과 검토

기능을 만들 때 AI에게 맡긴 내용을 남기고, 받은 코드를 그대로 쓰지 않고 구조와 알고리즘을 하나씩 물어서 고친 뒤 최종 문서를 남긴다. 미니프로젝트의 `prompts_log.md`도 이 기록에서 뽑는다.

### 7-1. 어디에 무엇을

| 파일 | 내용 | 언제 |
|---|---|---|
| `docs/<이름>/ai_log/<날짜>_<기능>.md` | 작업 기록 (아래 양식) | 작업할 때마다 |
| `docs/<이름>/최종_<기능>.md` | 기능 하나가 끝났을 때의 최종 설명 | PR 올리기 전 |
| 노션 | 최종 문서 복사본 | Merge 뒤 |

### 7-2. 작업 기록 양식

```markdown
# <기능 이름> — <날짜>

## 1. 맡긴 일
AI에게 무엇을 만들라고 했는지 (요청 요약, 기준으로 준 문서)

## 2. 받은 구조
클래스·함수 목록과 각자 하는 일, 처리 순서

## 3. 하나씩 물어본 것
| 물어본 것 | AI의 설명 | 내 판단 |
|---|---|---|
| 이 함수는 왜 이 순서로 처리하나 | … | 맞음 / 이상함: 이유 |
| 입력이 비어 있으면 어떻게 되나 | … | … |
| 계약의 어느 항목을 지키는 코드인가 | … | … |

## 4. 고친 것
이상하다고 본 곳, 고치라고 한 내용, 고친 뒤 결과 (시험 통과 여부)

## 5. 남은 것
아직 이해하지 못했거나 확인하지 못한 부분
```

### 7-3. 검토할 때 꼭 묻는 것

- 이 코드가 계약(포트 서명, 채널 JSON, 오류 코드)의 어느 줄을 지키는가.
- 실패하면 무엇을 돌려주는가. 예외를 밖으로 던지지 않는가.
- 원본 이미지·OCR 줄·후보 값이 로그·저장·공유로 나가는 곳이 없는가.
- 시험이 무엇을 확인하고, 무엇을 확인하지 않는가.

### 7-4. PR에 넣는 것

PR 설명에 `docs/<이름>/최종_<기능>.md` 경로와 작업 기록 경로를 적는다. 리뷰하는 사람은 3번 표(물어본 것)에서 "이상함"으로 적힌 곳이 고쳐졌는지 본다.

# 화면길잡이 설계 (러프 · 보완판)

> 무드 원안을 뼈대로 두고, 빠진 칸을 채웠다. **[보완]** 표시가 추가한 부분이고, 표시 없는 문장은 원안을 다듬은 것이다.
> 기능 범위는 중간 보고서 기준(`화면길잡이_기능_개념_정리.md` 0장). MVP에는 LLM이 없으므로 LLM 관련 칸은 "확장 자리"로만 둔다.

---

## 0. 변하지 않는 부분 / 변하는 부분

설계의 출발점. 변하지 않는 것은 엔티티·유스케이스 쪽으로, 변하는 것은 인터페이스 뒤(세부사항)로 보낸다.

| 변하지 않는 핵심 (원안) | 의미 | 설계상 자리 |
|---|---|---|
| ① 사진 속 내용을 구별하는 비전 인식 | 이미지 → UI 요소(글자 + 위치) | 엔티티: `UiElement` / 포트: `VisionRecognizer` |
| ② 앱마다의 지원 기능·사용법 정보 | 앱·버전·화면·기능·단계 | 엔티티: `GuidanceMap`(사용 백과사전) |
| ③ ①과 ②를 대조해 화면에 대입하는 기술 | 화면 식별 → 대상 찾기 → 강조 좌표 | 엔티티 규칙: `identifyScreen`, `findTarget` |
| ④ 민감 데이터가 기기 밖으로 나가지 않게 막고 알리기 | 개인정보 후보 검출·공유 전 확인 | 엔티티 규칙: `PiiDetector`, `merge` / 관문 |

| 변하는 부분 **[보완]** | 예 | 인터페이스로 감출 것 |
|---|---|---|
| 지원 앱·버전·기능 데이터 | 기능 맵 revision | `GuidanceRepository` |
| 비전·판단 모델 종류 | ML Kit → LiteRT 검출기, 규칙 → Jev 판단기 | `VisionRecognizer`, `Judge` |
| 입력 방식 | 카메라 / 갤러리 / 실시간 캡처 | `ImageSource` |
| 표시 방식 | 앱 안 안내 화면 / 다른 앱 위 오버레이 | `GuideRenderer` (같은 `GuideStep` 계약) |
| 기기·화면 비율 | 해상도, 미리보기 크기 | 좌표 변환기 `CoordinateMapper` |
| 저장·배포 기술 | 로컬 DB, Firebase → Supabase | `HistoryRepository`, `MapSource` |

> 원안의 확장 아이디어: ④만 떼어 내면 "회사 규정 데이터가 밖으로 나가지 않게 막는 전용 기기·앱"으로도 쓸 수 있다. → **개인정보 보호축을 다른 축에 의존하지 않게 만들면** 이 재사용이 가능하다. (MVP 범위 밖, 구조로만 열어 둠)

## 1. 수직 (엔티티 ← 유스케이스 ← 파서 ← 세부사항)

### 1.1 엔티티

원안의 세 묶음을 유지하고, 각 묶음의 M·C·V가 무엇인지 구체화했다. (내 규칙: `M → C ← I_V → V`, M은 C 안에, V는 인터페이스로 역전)

| 묶음 | M (순수 데이터) | C (처리자) | I_V / V (인터페이스와 구현체) |
|---|---|---|---|
| **앱 사용법** (원안: 사용법 DB) | `GuidanceMap`(package, versionRange, screenId, screenAnchors, actionId, utterances, selectors, steps, supportLevel) | `GuideMatcher`: 화면 식별·대상 찾기·단계 진행 규칙 | `GuidanceRepository` ← 로컬 DB 구현 / 시험용 메모리 구현. **[보완]** DB 자체는 세부사항, 엔티티는 데이터 모양과 규칙만 |
| **AI 비전 데이터** | `UiElement`(label, box), `Box`, `RecognizedScreen` | `ElementNormalizer`: 정규화·읽기 순서 정렬·빈 줄 제외 | `VisionRecognizer` ← ML Kit OCR 구현 / (확장) 접근성 노드 구현, LiteRT 아이콘 검출 구현 |
| **AI 제어 구성** (원안: 모델 종류·참조 데이터·컨텍스트/프롬프트/하네스) | `AiProfile` 구조체: 단계별 사용 모델, 참조 데이터(기능 맵 revision), 임계값(앵커 수 2, 편집거리 1, 3초) | `AiPipeline`: 6단계 처리 순서를 프로필대로 실행 | 단계별 포트(`VisionRecognizer`, `IntentRouter`, `Judge`, `PiiDetector`, `Explainer`). **[보완]** MVP는 규칙·템플릿 구현만, 프롬프트·하네스는 `Explainer`/`Judge`의 확장 구현 자리 |
| **개인정보 [보완]** | `PiiCandidate`(start, end, types), `PiiType`(enum) | `PiiMerger`: 병합·우선순위·날짜 제외 | `PiiDetector` × N (정규식 유형별, ML Kit 개체 추출) — Strategy |
| **안내 세션 [보완]** | `GuideSession`(입력 방식, 화면 ID, 기능 ID, 현재 단계), `FlowState`(enum) | `GuideSequence`: 상태 전이 규칙(Gate) | 렌더러 인터페이스 `GuideRenderer` ← 앱 화면 / 오버레이 |

원안의 "인식하라는 인터페이스는 엔티티 밖, 타입별 DB를 불러 연결한 게 구현체" → **포트(인터페이스)는 엔티티 쪽 패키지가 소유하고, 구현체는 바깥(세부사항)이 그 포트를 구현**한다. 의존 방향이 안쪽을 향해야 모델을 바꿔도 엔티티를 안 고친다(DIP·헥사고날).

### 1.2 유스케이스

원안 목록을 채우고, 각 경우의 "키맨"을 붙였다.

| 유스케이스 | 경우의 수 | 키맨 | 요구사항 |
|---|---|---|---|
| **화면 분석** | 카메라 / 갤러리 정지 이미지 1장 → 화면 식별 | `AnalyzeScreen` | F01, F02 |
| **실시간 안내** (원안) | 다른 앱 위에서 요청한 순간의 한 화면만 스캔 | `ScanCurrentScreen` | N01 |
| **앱·화면 식별** (원안: "앱이 이름이나 또는…") **[보완]** | 실시간: 패키지 이름(접근성으로 현재 앱을 앎) + 앵커 / 이미지: 앵커만으로 화면 식별 | `IdentifyScreen` | F02, N01 |
| **기능 선택·단계 안내** | 기능 목록 선택 → 단계 1..n → 완료 | `StartGuide`, `AdvanceStep` | F04 |
| **화면이 달라요 [보완]** | 같은 기능 ID를 유지한 채 재스캔·재촬영 → 새 후보 | `RescanForAction` | F04 |
| **데이터 내보내기** (원안: 임베디드 검사) | 공유 진입점 어디서든 → 후보 검사 → 확인 → 공유 | `PrepareShare`, `Share` | F03, F06, NFR-01 |
| **과거 기록 확인** (원안) | 저장 / 목록 / 다시 열기 | `SaveHistory`, `ListHistory`, `OpenHistory` | F05 |
| **기능 맵 갱신 [보완]** | 시스템이 시작: 새 revision 확인 → 검증 → 원자 교체 / 실패 시 유지 | `UpdateGuidanceMap` | B01, B02 |
| **권한·복구 [보완]** | 권한 거부 → 대체 경로 / 인식 실패 → 재시도 / 분석 취소 | `RecoverFromError` | C04, C05 |
| **선택적 동기화 [보완]** | 동의 시 기능 ID·단계·시각만 | `SyncHistory` | F05 |
| **모드 전환** (원안: 상태 패턴) | 홈 / 카메라 / 갤러리 / 실시간 / 안내 / 공유 모드마다 UI 구조 변경 명령, 백그라운드 기능 호출, 미리 활성화할 엔티티 | 관리자 `AppModeManager` | 전체 |

모드 전환에서 "미리 활성화할 것" 예 **[보완]**: 갤러리·카메라 모드 진입 시 OCR 엔진 워밍업, 실시간 모드 진입 시 권한 3종 확인·오버레이 서비스 준비, 공유 모드 진입 시 후보 검사 결과 준비, 앱 시작 시 기능 맵 로드.

### 1.3 파서 계층 (데이터 계층)

원안: "외부 앱 데이터 연계 시 받아들이는 번역 클래스". 실제로 번역할 외부 형식이 다섯 군데 있다. **[보완]**

| 파서 | 바깥 형식 → 안쪽 형식 | 위치 |
|---|---|---|
| `MlKitTextParser` | ML Kit `Text`(블록·라인) → `UiElement` 목록 | Kotlin |
| `AccessibilityNodeParser` (N01) | 접근성 노드 트리(텍스트·역할·좌표) → `UiElement` 목록 | Kotlin |
| `GuidanceMapParser` | 배포 패키지(Firestore 문서/파일) → `GuidanceMap` + 해시·서명·스키마 검증 | Flutter |
| `ChannelCodec` | MethodChannel `Map` ↔ `AnalysisResult` DTO (양쪽에 하나씩) | Flutter·Kotlin |
| `CoordinateMapper` | 이미지 픽셀 좌표 ↔ 미리보기·실제 화면 좌표 (기기·비율 차이 흡수) | Flutter·Kotlin |
| (확장) 공식 연동 파서 | 공식 API·딥링크 기능 정의 → Capability Registry 항목 | — |

### 1.4 세부사항

| 원안 | 보완 |
|---|---|
| 휴대폰 기종, 화면 비율 | → `CoordinateMapper`가 흡수. 기능 맵 선택자는 정규화 좌표, 절대 좌표는 마지막 폴백 |

| **[보완]** Android 시스템 | 권한, AccessibilityService, MediaProjection, WindowManager 오버레이 |
| **[보완]** 채널 | `screen_guide/analyze`, `screen_guide/overlay` |

## 2. 수평 (핵심 기능별 축)

원안의 네 축에 세 축을 더했다. UI 설계서 30쪽의 통합 구조(Capability Registry + App Guidance DB + Local Privacy Guard + Overlay Runtime)와도 맞춘다.

| 축 | 원안 | 하는 일 | 소유 상태 | 대응 |
|---|---|---|---|---|
| **앱 흐름 관리자** | ○ | 모드 전환, 안내 세션 단계 시퀀스(FlowState·Runner·Gate) | `GuideSession`, 현재 모드 | 시퀀스 관리자 |
| **에이전트 시스템축** | ○ | 비전 인식, 의도 라우팅, 판단, 설명. MVP = ML Kit + 규칙 + 템플릿, 확장 = Jev 판단기·임베딩·소형 LLM | 없음(무상태) | AI 처리 6단계 |
| **리소스 매니저** | ○ | 데이터 입출력: 기능 맵 로드·갱신·롤백, 이력 저장, 촬영 복사본 정리 | 활성 revision | 리소스 관리자 |
| **사용 백과사전 축** | ○ | 앱·화면·기능·단계 조회, 지원 범위 판단(버전 불일치 시 강조 중단) | 기능 맵 내용 | App Guidance DB |
| **개인정보 보호축 [보완]** | | 후보 검출·병합, 공유 전 확인 관문, 원본·원문 반출 금지 | 후보 목록, 확인 여부 | Local Privacy Guard |
| **입력·캡처축 [보완]** | | 카메라·갤러리·실시간 캡처, 권한, 이미지 1장 보장 | 선택 이미지 경로 | — |
| **표시(렌더러) 축 [보완]** | | 앱 안 안내 화면 / 오버레이 런타임, 16pt·강조 규칙 | 표시 여부 | Overlay Runtime |
| (확장) 공식 연동축 | | 공식 API가 있는 앱의 기능 ID 호출 | 등록부 | Capability Registry |

축끼리의 규칙: 직접 호출하지 않고 계약(DTO·인터페이스)으로만. 특히 **개인정보 보호축은 다른 축을 몰라야** 0장의 재사용 아이디어가 산다.

## 3. 규모 **[보완]** (원안에 없던 축)

| 규모 | 결정 |
|---|---|
| 시스템 (스타일) | 온디바이스 모놀리식 앱 + 기능 맵 배포에만 클라이언트–서버. 분석 내부는 파이프–필터(입력 정리 → 라우팅 → 판단 → 탐색 → 안전 검사 → 설명) |
| 영역 (패턴) | Kotlin 분석 코어 = 헥사고날(포트: `VisionRecognizer`, `EntityExtractor`), Flutter 화면 = MVC, 기능 맵·이력 = Repository, 채널 = 코덱으로 외부 형식 격리 |
| 클래스 (디자인 패턴) | 개인정보 유형 = Strategy, 안내 단계·앱 모드 = State, 버튼 = Command(기능 ID), AI 단계 교체 = 포트 + 생성자 주입, 상태 → 화면 = Observer, 렌더러 둘 = 같은 계약 다른 구현 |

## 4. 프로세스 **[보완]**

| 진입 주체 | 시작하는 것 | 끝·중단 |
|---|---|---|
| 사용자 | 촬영·선택, 분석, 기능 선택, 다음 단계, 공유, 기록 열기 | 취소, 화면이 달라요, 인식 끄기 |
| 시스템 | 앱 시작 시 기능 맵 확인, 모드 진입 시 워밍업 | 검증 실패 시 이전 revision 유지 |
| OS·외부 | 권한 결과, 공유 시트 결과, 오버레이 권한 철회 | 철회 즉시 오버레이·캡처·서비스 해제 |

안내 세션 상태: `IDLE → PICKED → ANALYZING → IDENTIFIED → GUIDING(n) → DONE` / 예외 `DENIED`, `ERROR(code)`, `CANCELLED`. 실패는 `ErrorCode` 타입으로 나눠 오류 화면이 코드별 문구·복구 버튼만 고르게 한다.

## 5. 핵심 로직 (원안 10장 그대로 유지)

원안에 붙여 둔 판단 규칙 표·AI 처리 6단계·외부 앱 연동 경로는 그대로 쓴다. 보완할 점 두 가지만:

- **불변식 추가 [보완]**: 원본 이미지와 OCR 원문 전체는 Kotlin 모듈 밖으로 나가지 않는다 / 기능 맵 교체는 원자적 / 후보 0건이어도 공유 전 확인 화면은 뜬다.
- **좌표 [보완]**: `boundingBox`는 원본 이미지 픽셀 기준이다. 미리보기·오버레이에 그릴 때 `CoordinateMapper`로 변환해야 강조 위치가 맞는다 (기기·화면 비율 = 세부사항 칸과 연결).

## 6. 프론트 연결 **[보완]** (5계층 한 줄 요약)

| 계층 | 화면길잡이 |
|---|---|
| 1 렌더러 (셸·셀) | 셸: `AppShell`(홈·기록·설정), `GuideShell`(입력~완료), `ShareShell`(P·SHARE), `OverlayShell`(Kotlin, LP~LG). 셀: 큰 버튼, 안내 카드, 강조 상자, 단계 표시줄, 후보 칩, 오류 패널 |
| 2 계약 | 화면 계약(화면별 상태 + 기능 ID), 흐름 계약(ask·wait·confirm·complete), 기능 계약(기능 ID ↔ 유스케이스), 클래스 계약(포트·리포지토리 인터페이스) |
| 3 조립기·등록부 | `bootstrap()`에서 실제/가짜 구현 주입, `ActionRegistry`가 모든 버튼에 핸들러가 있는지 시작 시 검사 |
| 4 런타임·관문 | Gate(상태별 허용 기능), 권한, 중복 분석 차단, 3초 제한, 취소 |
| 5 기능 | 기능 ID → 핸들러 → 1.2의 유스케이스 |
